# Mobile terminal candidate authority proof

Task `td-ef9c30` extends the local mobile catalog from managed-shell-only attachment to explicit worktree terminal candidates. The isolated branch started from Sidecar `1927f634e041ea9bb30210d5e8e0d55819c19be9`. The versioned wire contract and source inventory extraction were reviewed and committed separately as `0d8eb230303b4ca7dc04e1ca2ac47357b9561dcd` and `940cc1c717d1e000be7f7066b852c43dc92e866b`; this document covers the owning resolver and production CLI/service path built on them.

## Authority contract

A worktree row exposes zero, one, or several server-owned terminal candidates. Zero is explicitly unavailable. One candidate becomes the row's direct ready target. Several candidates leave the parent row ambiguous and non-authoritative while each child carries its own opaque selector and exact expected target identity. The client displays the server labels and sends the selected selector and paired expected identity unchanged; it does not parse tmux names, infer ownership, or choose by order.

The selector is deterministic across fresh API processes and binds the owning host, workspace identity, canonical project and worktree paths, and the complete ordered set of current session/pane identities. The expected target additionally binds owner configuration, tmux server PID, session ID and creation time, and the selected pane. A candidate selector is rejected at the raw service boundary when its paired expected identity is absent. Any missing project, failed or stale project observation, changed worktree membership, changed complete candidate set, removed pane, same-name pane replacement, or mismatched expected identity refuses attachment without fallback.

Catalog authorization uses the exact inventory observation already collected for the snapshot, so several candidates do not trigger repeated global catalog scans. Fresh-process resolve performs a fresh catalog discovery once. After resolve, each control/input/resize/heartbeat/release/history boundary uses the narrow target revalidator: it reads current owner configuration, finds the exact configured project, runs Git worktree inventory for only that project, refreshes the global tmux pane list without provider capture, inspects the exact selected pane, repeats the narrow source refresh, and compares all bound identity. Durable shell manifests for every configured project are read cheaply so a shell owned by another project cannot enter the selected worktree merely by changing directory. This keeps exact authority while avoiding the roughly six-second full real-hub catalog path on each key or heartbeat.

The shared inventory addition is state-free terminal-source projection. `RefreshWorktreeTerminalCandidates` reuses the same path ownership, nested-project, Sidecar chrome, preferred worktree session, dead-pane, and durable shell reservation rules as the desktop Sessions collector. It clears residual pane/session fields for the narrow authority read, so removed matches cannot survive from a previous observation. It performs no Git lookup or terminal capture itself; the owning caller brackets it with current membership and exact-pane inspection.

## Isolated real service journey

`./scripts/mobile-candidate-proof.sh /private/tmp/sidecar-mobile-candidates-final8 "$(command -v tmux)"` builds the actual CLI and runs it with an explicit private config, `XDG_STATE_HOME`, `SIDECAR_ISOLATED_STATE=1`, and tmux socket. Every direct tmux command uses the private `-S` path with `TMUX` and `TMUX_PANE` cleared. The proof creates one temporary Git project and synthetic shell panes only, never captures a current user session, and its trap stops only the server marked as owned by that proof root.

The real catalog reports the same worktree as unavailable with zero candidates, directly ready with one candidate, and ambiguous with two candidates. Killing the selected pane before a fresh service resolve rejects the old selector with `identity_changed`; recreating the same session yields a new pane and selector. A selected candidate then acquires control and accepts 15 literal-input and 15 heartbeat operations while its pane emits synthetic output. All 30 mutations use the narrow current-source revalidator. Median response time is 39.000 ms, p95 is 41.491 ms, and maximum is 42.352 ms on this local proof. Twenty-six strictly increasing full frames reach the client, current synthetic output is visible, and no reset occurs during ordinary output or mutations.

Adding a third candidate while the selected pane remains unchanged makes the next heartbeat fail `identity_changed`, proving that complete-set drift revokes authority. A fresh API process then opens the restored two-candidate selection; killing and recreating the same selected session makes its next heartbeat fail `identity_changed`. Conditional cleanup leaves the new session's owner empty.

The same private journey creates a horizontally split tmux window and lists both of its panes as distinct candidates. It selects pane `%5`, acquires a verified 46×23 pane while sibling `%6` remains 39×23, then resizes the selected pane to a verified 50×20 while the sibling remains 39×20. Input appears in `%5` and is absent from `%6`. Multi-pane geometry grows or shrinks the containing window by the selected pane's requested delta, adjusts the exact selected pane, and reads the pane geometry back before acknowledging control or resize. Its conditional tmux mutation binds the ownership token and the observed window ID, pane count, window size, and pane size, so external layout drift refuses before applying a stale delta. A layout that cannot produce the requested pane size refuses and conditionally clears ownership rather than emitting a false accepted geometry. The structured result is `/private/tmp/sidecar-mobile-candidates-final8/result.json` (SHA-256 `4cb21b7ce1bd3395c3d25900c8f77a848fabe09897993b8a9f7af0c074cefa0f`) and the tested binary is `/private/tmp/sidecar-mobile-candidates-final8/sidecar` (SHA-256 `6baf5b4e5976f9dc11ecce888738bffbadd511fddfb466601e6327634857f60f`). The shell and Python proof drivers have SHA-256 `5860744ca4908d011a325ab914aa2452be40a8d6e0f8d6e0d081bff8ce1c3cfe` and `8830bbf5bcce25bb603e1b78ca2dca43d1464d064d57ff43652eb8c11d3ad3ff` respectively.

The proof covers separate candidate sessions and one real horizontal split, the common worktree-agent and basic multi-pane shapes. It does not claim that every arbitrarily nested tmux layout can satisfy every phone geometry; those requests fail closed on the measured pane dimensions.
