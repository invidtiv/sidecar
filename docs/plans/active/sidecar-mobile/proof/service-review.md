## Continuous-output resize finding, resolved

**A queued capture from before resize could be published as the new reset generation.** An independent macOS Swift executable imported the actual `SidecarClient` package and used a temporary `/usr/bin/ssh -T` process transport against a fresh isolated service. It applied frames after an 80 ms delay while the terminal emitted continuous output. Two runs observed `resized` accepting 70×20 at reset generation 2, followed by a full frame at sequence 3/reset 2 still sized 80×24, then sequence 4/reset 2 at the accepted 70×20. The client could acknowledge a supposedly current full frame and unlock input while displaying the old geometry. `publish` waited for the operation lock with an already captured snapshot and relabeled it after resize advanced the reset.

The fix tags each queued capture with the reset observed by its callback and drops captures from an older reset before assigning a current output checkpoint. Deliberate control/resize requests a fresh capture after its acknowledgment and reset; expected geometry is a second fence. Replacing an obsolete capture with a newer reset's full frame is distinct from same-generation queue overflow. Independent source inspection verified the provenance boundary: `captureFinished` invokes the subscriber callback synchronously through `subscriberDeliveryGate.invoke` on the same ordered actor that later invokes the resize completion-marker callback. A pre-resize capture cannot be tagged after that marker acknowledgment. Focused regressions cover queued same-size pre-resize captures, cross-reset replacement, and actual overflow.

The final combined SSH journey passed with 27 applied frames, an 80 ms artificial application delay, and terminal output every 120 ms. The first replacement frame had the accepted 70×20 geometry. Release and a second SSH/API process reconnected view-only at attachment generation 2; one input request was sent on the first connection and none on reconnect. No client errors occurred. `/tmp/sidecar-mobile-swift-client-review/result-v5.json` has SHA-256 `27dfe68d5b7545632902449e3e6610638fcb5862f5768ce1ad730b7e6deba55e`; synthetic wire logs are the `.v5` copies beside it. All proof servers were cleaned. This is actual Swift protocol-client consumption with a test process transport, not UIKit rendering or native-device latency evidence.

## Resolved findings

1. **Nested tmux acknowledgment correlation.** A real private-server probe showed outer success followed by a nested resize failure, with identical response flags; the original callback accepted the outer success and could shift subsequent callbacks. `SendUntilMarker` now drains the complete transaction through a unique top-level completion marker, includes nested failures in the result, and poisons the channel on timeout. Minimum/current tmux probes and focused regressions cover successful, failed, and false branches.
2. **Lost mobile presence.** A process remaining alive no longer implies current authority. The attachment checks a 15-second deadline before mutations and expires control independently; the real idle-pause proof confirms that a late heartbeat cannot restore it.
3. **Post-reset acknowledgment.** Mutations now require an output sequence identifying an emitted full frame from the current reset generation. Merely echoing a reset generation does not authorize input. Acknowledgment may lag newer frames within that generation.
4. **Durable shell incarnation.** The resolver binds the managed shell's `CreatedAt` separately from tmux session creation. Replacing only the durable record now refuses input and releases control in the live proof.
5. **Legacy metadata layout.** Capture carries an explicit full/legacy layout; a comma-rich desktop title cannot select the new parser. Focused regressions preserve the legacy path.
6. **Bounds and failure cleanup.** Target handles, active attachments, initial geometry, and outbound queues are bounded. Failed subscription closes the new attachment. Queue overflow or writer failure is terminal, fences subsequent mutations, and serializes attachment release before manager shutdown.
7. **Strict envelope validation.** Missing version and malformed trailing JSON, both accepted by the initial isolated hello probe, now refuse through explicit version-presence and end-of-input checks.
8. **Actual cursor metadata.** The renderer handles tmux's `bar`, `underline`, and `block` values and blinking metadata. The private-server probe's blinking bar is represented; missing metadata remains a documented cosmetic approximation.
9. **Distinct control lifetimes.** The server-derived owner includes a new control epoch, preventing an old conditional release from matching a reacquired lease. A claim whose owner write succeeds but resize fails conditionally cleans only that exact token.
10. **Fresh-process reconnect.** The coordinator identified that old handles cannot survive the SSH process that owned their maps. Reconnect now supplies a locator and exact expected stable identity, revalidates in Go, returns new process-local handles and a view-only attachment, and never replays input. Stable target generation excludes the API instance. Both owner and independent actual SSH proofs use distinct service processes.
11. **Idle recovery after expiry.** The live hazard pass first observed reset generation 2 without a replacement frame, preventing explicit control until unrelated pane output. Expiry now requests an authoritative capture through the existing ordered control actor. The final live retest gets reset plus replacement after 15.971 seconds and reacquires control without unrelated output.

A second private tmux probe showed why fixed nested-response counts alone do not solve finding 1: after an early nested `set-option` error, tmux skipped the remaining nested command and proceeded to the next top-level completion marker. The selected marker barrier handles that shortened branch without allowing the next normal response to satisfy an old callback. The bounded writer now treats failed delivery as terminal rather than silently dropping a correlated acknowledgment while permitting later mutations.

All findings were sent directly to the implementation owner. The private probes used explicit `-S` paths under newly created temporary directories, removed inherited `TMUX` and `TMUX_PANE`, and cleaned only their own private servers. The hello-only helper used its inspected isolated state/config/socket wrapper and opened no target. No default tmux server or live Sidecar state was mutated.
