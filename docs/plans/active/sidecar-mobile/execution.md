Proposed production packages are `internal/mobile` for the service and `internal/mobileproto` for the wire envelope. Final names can follow the first extraction; do not add a generic remote-control framework. The API runs as `sidecar mobile serve --stdio` with no PTY. Catalog/status queries get documented JSON CLI paths. Terminal control is already a documented non-interactive API path; duplicating it into a second low-level prompt system is unnecessary.

The Go service owner owns `testdata/mobile-protocol/v0/` in Sidecar. The initial spike owns its `experimental-terminal/` child until review transfers it. The Swift owner consumes a vendored read-only snapshot under the mobile client's test fixtures with a manifest recording the Sidecar commit and SHA-256 values, plus one explicit sync command. No symlinks into a sibling checkout and no separate hand-maintained golden corpus. The fixture owner changes both producer expectations and the manifest; the consumer proves decoding and resulting emulator behavior against that pinned revision. Make the spike namespace visibly experimental and do not advertise wire compatibility until its shape is settled.

The production envelope should specify protocol version, request/attachment IDs, output sequence, reset boundary, accepted operation acknowledgements, capability/refusal codes, and finite message/buffer bounds. The exact constants and seed representation are selected and measured in the spike. Protocol mismatch fails before opening a terminal. Do not send secrets, real terminal transcripts, or private host credentials into fixtures.

**Reviewed result (2026-09-07):** td-415417 and td-322041 passed independent cross-review. Capture seed plus raw continuation was falsified by hidden rendition and wrap state. The Go spike owner starts in a fresh isolated Sidecar worktree and runs `make worktree-init` first. Package-local tests can inspect existing private seed methods without adding a public production API. The Swift spike owner owns `../sidecar-mobile/Spikes/TerminalSeed/**`, consumes those fixtures, and uses the pinned SwiftTerm emulator without importing Jumar application code. This division permits early harness setup while the producer finishes fixtures.

Evaluate these alternatives in order; record the selected strategy, rejected alternative and observed cost in spike evidence:

1. **Explicit snapshot plus ordered VT output:** emit a reset/seed that restores the required current terminal state, then exact post-seed bytes. Prove main/alternate screen restoration, cursor, rendition, scrolling and input modes using SwiftTerm. Every state that cannot be reconstructed is an explicit support limit, not a default inferred from a blank emulator.
2. **Server-normalized frames with explicit input state:** if exact raw continuation is unsound, use canonical full/delta screen presentation from the Go owner and an explicit input/geometry contract. Prove that the chosen SwiftTerm rendering adapter does not reinterpret normalized frames as a second independent application stream; measure bandwidth, selection, history and cursor behavior. The result must still be a live interactive terminal, not text polling passed off as complete fidelity.
3. If neither meets the required agent journey, stop production extraction and report the specific failing state and smallest next experiment. A normal PTY `tmux attach`, unbounded transcript replay, or dropping unrecognized sequences silently does not satisfy this gate.

The required corpus is small but adversarial: a colored shell with trailing colored blanks; a live agent TUI in alternate screen; exit back to the saved main screen; cursor movement and hidden cursor; Unicode/combining/wide cells; wrap and scroll boundaries; bracketed multiline paste; application cursor/keypad behavior; a terminal query with exactly one reply owner; output racing the seed; a simulated sequence gap/overflow; resize and reconnect with queued input. Include a terminal whose rendition/modes were set before attachment, since a fixture that emits all modes after attach hides the hard problem. Record any supported-agent limitations before deciding whether the gate is sufficient.

The geometry portion tests two distinct attachments in one hub process, background/disconnect evidence expiry, stale release after a new owner, lease-read failure, wrong server incarnation, and changed target generation. It must establish how mobile identity fits the host/PID contract and host-side `sidecar open`/layout refusal. Avoid changing the shared lease token format unless the audited existing contract cannot represent safe attachment identity.

**Pass:** the Go producer and SwiftTerm consumer agree on the required screen/input state before and after continuation; stream discontinuities reset instead of silently diverging; input is never replayed; the selected lease identity has a credible live/disconnect path; independent review accepts the proposed production shape. Record unsupported modes and measured overhead. One emulator accepting a fixture is insufficient.
