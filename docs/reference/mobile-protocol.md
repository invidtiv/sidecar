# Mobile terminal protocol v0

`sidecar mobile serve --stdio` is the authenticated SSH exec endpoint used by the native Sidecar client. It reads and writes newline-delimited JSON. The SSH channel must not allocate a PTY. Each envelope has `version: 0`, `type`, and a unique bounded `request_id`; the server closes on a version mismatch. The maximum encoded line is 8 MiB. When registered remote hosts are enabled, this command is the hub: it composes their owning catalogs and forwards one selected terminal stream to the exact owning Sidecar. Hubs invoke `sidecar mobile serve --stdio --owner-only` remotely. That internal mode serves only the machine where it runs, preventing reciprocal host configurations from forming recursive hubs.

The first request is `hello`. `status` reports the same capabilities. `resolve` takes a `target` selector and returns a process-scoped opaque target handle plus the exact stable identity the server resolved. The local service resolves Sidecar-managed shells and exact catalog-issued worktree terminal candidates. Unregistered arbitrary tmux panes, oversized panes, changed source identity, and ambiguous selectors are refused.

`sessions` returns the bounded Sessions catalog owned by the hub process. Its optional `catalog_query` contains `sort` (`activity`, `project`, `recent`, or `name`), `search`, repeatable `hosts`, `providers`, and `states` filters, and the tri-state `show_idle_sessions` preference. Explicit `false` matches desktop Sessions with **Show idle sessions** off by excluding only rows in the shared `No Session` group. It does not infer visibility from lifecycle `idle` or an attachment refusal. Explicit `true` includes those rows, while omission preserves the v0 legacy all-row query. Search, sorting, activity groups, project groups, and recent buckets use the same state-free `workspacelist` rules as desktop Sessions. Each online owner's unfiltered Project-order snapshot is validated and remapped before the hub applies this one final query, so older owner services never need to understand the additive preference, configured project order is retained, and equal raw project IDs on different hosts remain separate. Disabled, connecting, stale, unsupported, and failed owners remain explicit host failures while available local and remote rows are returned. The combined query text is limited to 512 bytes, each filter kind to 32 values, hosts to 128, rows to 2,048, and collection failures to 128. Owners are queried concurrently, one catalog stream each, under a whole-query deadline; at most eight owner catalogs are outside the aggregate budget at once (being read, or read and not yet charged); each remote owner also has its own deadline, while the hub's local owner is bounded only by the query, so a busy hub is never reported as its own failed host. Cumulative rows, candidates, and encoded bytes are charged as each owner's catalog arrives, before it is retained; the first arrival that overflows refuses the query at once and cancels the owners still running. Sources are composed and failures reported in directory order. A long-lived hub (the UI API) shares one local inventory collection between concurrent requests: a request joins one in flight or reuses one that started under 1.5 s ago, never across a catalog change signal, owner config generation change, or tmux server change (socket device, inode and modification time). Only collected inventory (rows, panes, and Git worktree discovery) is shared; each request authorizes its rows with its own read of shell manifests and registered worktrees and its own tmux pane listings, and re-derives worktree terminal candidates from its own listing and the shell reservations in the manifests at that moment, so a row is advertised attachable only if the current resolver accepts it. The producer also checks the fully JSON-encoded snapshot against the line limit with room for the stdio response envelope. Unknown sort values, exceeded collection bounds, and an oversized serialized result are refused as errors by both CLI and service paths.

Each catalog row may include `path`, the owning workspace's filesystem path, falling back to that workspace's project root when its path is empty. Managed shells project the deepest current Git workspace containing their durable `workDir`; unknown or legacy directories fall back to the configured project root. This does not follow a terminal’s transient cwd. It is human-readable presentation metadata on `owner_host_id`, never a scoped key or terminal selector. The hub preserves a remote owner's path verbatim while remapping IDs and attachment authority; clients must not interpret it as a local filesystem path. Older rows may omit it, and omission remains valid.

Local rows and worktree candidates also expose optional `content_workspace_id`, the public selector clients pass unchanged as `workspace` to the UI API's project content, tree, layout and viewer-presence routes (and content subscriptions). Empty or absent selects the configured project root; nonempty names its owning linked worktree. Shells and candidates sharing a root share this value, consistently with `path` and the content/layout/relay resolver. Configured symlink aliases preserve durable shell lookup. This selector is independent of `workspace_id` and `TargetIdentity.expected_target`: terminal resolution, generation checks and attachment authority remain unchanged. Clients never derive it from opaque row IDs, candidate selectors or terminal identity. Hub-remapped remote rows and candidates omit it because those UI API routes do not forward remote content/layout/presence; absence on a remote row does not authorize a local read. Older producers may omit it, so an older linked row requires an updated producer to supply its content selector. Fixture catalogs supply linked selectors and preserve the legacy root shell's configured-root behavior. See [project content and viewer layouts](ui-api.md#project-content-and-viewer-layouts).

Catalog rows also include `main_checkout`, true only for the owning project's main Git checkout and false for other worktrees and managed shells. This presentation fact is preserved during hub remapping and shares the CLI/HTTP catalog type. Older producers may omit it; clients treat absence as unknown. Project and workspace paths are canonicalized on their owning host, never through the hub's local filesystem. Direct shell terminal selectors are exact session identities, including literal selector-like names; a missing session cannot fall back to a display name.

Every catalog snapshot carries the hub, owning-host, and configuration-generation authority that produced it, an observation time, a generation over the final authorized row facts, explicit host states, ordered sections, and project collection failures. Every row carries its source-backed catalog `id` and `project_id`, owning host, observed status, live/ambiguous/stale facts, and one attachment verdict. State filters run against that final verdict, including resolver failures. `workspace_id` is present when the row has been resolved into the terminal service's stable workspace identity:

- `ready` includes a target selector and `expected_target`, the full server-resolved identity that selector named at observation time.
- `unavailable` has no live unique pane.
- `ambiguous` has multiple pane matches or a terminal selector claimed by multiple rows.
- `stale` has stale collection or changed identity.
- `unknown` lacks durable managed-shell identity.
- `unsupported` is visible but cannot be opened by this protocol slice.

Worktree rows carry a source-owned candidate set derived from current project/worktree membership, durable shell reservations, and exact tmux session/pane observations. Zero candidates makes the row unavailable. One candidate makes the row directly ready. Several candidates keep the parent row ambiguous while exposing explicit selectable children. Each child has a server label, an opaque deterministic selector, and its own complete `expected_target`; clients do not derive or parse selectors. A row contains at most 16 candidates and a snapshot contains at most 2,048. Catalog validation rejects selectable candidates on non-live, stale, ambiguous-one-candidate, or non-online-host rows.

Selecting a `ready` row sends both its `target` and `expected_target` in the subsequent `resolve` request. The server resolves the selector again and exact-matches the expected hub, host/config generation, workspace/session/pane, tmux server incarnation, and target generation before issuing an opaque handle. A same-name replacement between catalog and resolve is therefore refused as `identity_changed`. Through a hub, only that mismatch (or a target from another hub) is `identity_changed` with `retry: false`; an owner that is unreachable, still connecting, or too slow to answer is a retryable `backend` refusal, so a client keeps retrying rather than treating a live terminal as replaced. An owner that will not come back by retrying is refused with `retry: false`: one no longer configured is `target_not_found`, one disabled, one that does not serve terminals, or a route the owner reports unsupported is `unsupported`, and a route the owner reports replaced is `identity_changed`. A target name by itself is the explicit M0 direct-resolution path and does not inherit a catalog row's readiness. Catalog collection can perform Git, state, process, and tmux reads, so a terminal stream with a live attachment refuses `sessions`; clients query on a catalog-only stream or after closing its attachment rather than delaying input and heartbeat handling.

Remote public selectors and expected identities are derived from the hub configuration generation, the exact stable host registration, and the owner's raw identity. Owner handles never leave the router. A fresh terminal SSH process reconstructs the same binding by obtaining a new current owner catalog; if that selected owner is still making its initial host connection, lookup waits only for that owner within the existing request deadline, then reloads the directory before continuing. It never waits for an unrelated offline host and never falls back to a same-named local terminal. Host removal, disablement, retargeting, runtime client replacement, stale health, owner configuration drift, pane/server replacement, protocol failure, or capability loss closes or refuses the route.

The host observation protocol advertises `mobileOwnerServeV0` separately from the older `mobileServeV0` bit. A hub requires the explicit owner-only capability before constructing the fixed remote command, then validates the actual mobile `hello` returned by that process. Older builds that know the local mobile protocol but cannot prevent recursive routing remain visible as unsupported owners. The forwarded owner's negotiated mobile capabilities must exactly match the public v0 contract. The hub forwards correlated JSONL without parsing terminal state, inventing heartbeats, retrying input, or changing operation/output/reset sequences. Phone EOF and route failure close owner stdin and the SSH exec so the owning service conditionally releases its own exact lease.

A worktree candidate selector additionally binds the canonical project/worktree source and the complete ordered candidate set. It is accepted only with its paired `expected_target`, including when whitespace surrounds the selector. Fresh resolve re-enumerates the source. Every later terminal operation uses a narrow current-source check that re-reads owner configuration, project membership, global durable shell claims, complete candidate membership, and exact pane/server incarnation without repeating the full catalog and Git scan. Any membership, configuration, or pane identity drift refuses the operation without falling back to a same-named target.

`open` takes `target_handle` and a client-generated diagnostic `attachment_id`. It returns an opaque `attachment_handle`, attachment generation 1, and reset generation 1 before any asynchronous event for that attachment. Handles and `api_instance` are valid only for this server process.

Every full frame carries `attachment_handle`, `attachment_generation`, strictly increasing `output_sequence`, `reset_generation`, geometry, terminal modes, `render_vt_base64`, and an advisory `history_size`. The decoded bytes are a complete normalized VT replacement generated from an authoritative ordered tmux capture. The receiver replaces its parser on a newer reset generation and applies only a contiguous sequence within a generation. v0 emits full frames only. It never forwards terminal replies produced by the native emulator back to tmux.

`history` reads one immutable normal-buffer snapshot on an existing attachment. It is read-only and does not require control or consume an operation sequence. The request carries an already-applied `last_output_sequence` within the current reset generation, exact applied `columns` and `rows`, and `history_rows` from 1 through the advertised maximum of 600. The checkpoint may lag newer frames in the same reset generation so continuous output does not starve the read. The frame's `history_size` is only a hint for whether the UI should offer history; zero or a stale value does not prevent an explicit request.

The correlated history response echoes the applied checkpoint and geometry. Its `history` object contains the capture-time history size, delivered history row count, descriptive half-open `start_line` and `end_line`, `at_oldest`, and a normalized VT payload. Feeding that payload once into a separate terminal at the response geometry with scrollback set to `history_rows` reconstructs exactly those latest history rows followed by the same capture's momentary live grid. The producer disables autowrap and cursor display, separates rows with CRLF, and does not advance after the final row. The history surface stays frozen until explicit refresh or return to live; it never receives or accumulates live full frames and cannot mutate the live parser, selection, input, or geometry lease.

History captures are limited to 600 rows and 4 MiB of normalized VT under the 8 MiB JSONL line bound. The owning service validates the attachment, durable target and owner configuration, reset, applied checkpoint, normal-screen state, and geometry before capture, then validates identity, configuration, reset, geometry, and screen state again before responding. Alternate-screen history, changed identity or geometry, a reset during capture, future or pre-reset checkpoints, inconsistent row bounds, and oversized output are refused. The offsets describe this snapshot only and are not reusable pagination authority. tmux may rotate its oldest retained rows without changing `history_size`, so older pagination remains deferred until the owner can issue an immutable snapshot token or a proven append/trim revision.

Control, input, resize, heartbeat, and release form one strictly increasing `operation_sequence` per attachment generation. Every request also carries `last_reset_generation` and `last_output_sequence`. The latter must identify an emitted full frame in the current reset generation; it may lag newer frames from the same generation. A sequence gap, future output sequence, stale reset, identity change, lease uncertainty, or transport failure refuses the mutation and revokes control. A refused mutation never consumes its `operation_sequence`; that includes a `release` whose lease clear fails, which still revokes control, so the client retries with the same sequence number. Successful mutation responses echo the operation sequence and current output/reset sequence. An accepted input response means tmux acknowledged `send-keys`; it does not claim the foreground application processed the bytes. Input is bounded standard base64 and is never replayed.

The required input-mode probe covers bracketed paste, application cursor keys, and application keypad. Unknown required input state permits viewing but refuses control. Mouse state affects native input encoding. Scrolling has no request type of its own: when the frame reports `mouse_any`, a client encodes a scroll gesture as SGR (or legacy, when `mouse_sgr` is false) wheel reports and sends them as ordinary `input` bytes. A pane without mouse reporting receives no scroll input bytes. A normal buffer is read through `history`; an alternate screen without mouse reporting has no gesture scrollback. Clients must never synthesize cursor-key presses for a scroll gesture, because those keys can navigate prompts or edit application state. Clients are expected to coalesce a gesture so that one `input` request carries a whole flush of reports rather than one request per notch. Missing cursor shape/blink metadata is cosmetic and falls back to a block cursor. tmux 3.4 does not expose `bracket_paste_flag`, so the current minimum-version path is view-only until a separate authoritative probe is implemented; tmux 3.7c exposes the required input fields.

A deliberate control or resize geometry change preserves control, returns the correlated response with a newer reset generation, then emits `reset`, then a replacement full frame. Further mutation waits until the client has applied that frame. For a multi-pane worktree candidate, the owner service binds the observed window ID, pane count, and window/pane extents in the same conditional tmux mutation as the lease token, adjusts the exact selected pane, and reads its accepted geometry back before acknowledging. Concurrent layout drift or a layout that cannot produce the requested pane size is refused and the attempted lease is conditionally cleared. Overflow, unrequested geometry change, alternate-screen transition, capture/identity failure, and mobile presence expiry revoke control and advance the reset generation. Each `reset` carries a `reason` from the fixed set in [Reset reasons](#reset-reasons). Every reset is followed by a replacement full frame, including on an idle pane: after a capture failure the service asks for a fresh capture itself, restarting the capture source if it died, and retries with a backoff that starts at 250 ms and caps at 5 seconds while the source keeps failing. A capture failure first revalidates the target with the same narrow current-source and exact-identity checks every operation uses, through an independent bounded local read rather than the capture connection that just failed. If the session or pane is gone, or its identity changed, the attachment ends instead of retrying: the service emits one asynchronous `error` with that refusal code (usually `identity_changed`) and `retry: false`, emits no `reset`, conditionally releases its lease, and stops capturing. If the capture transport died before lease teardown, release uses a bounded local tmux command that compares the exact lease token and bound server/session incarnation before clearing it; it never sends input or resizes through that recovery path. The attachment handle is then invalid (`attachment_invalid`), and the client resolves the target again or reconnects. A check that is inconclusive, such as one that times out, keeps the retry. Heartbeats are advertised every 5 seconds; after 15 seconds without heartbeat or input, the server conditionally releases only its exact current tmux owner token. Explicit control is required afterward.

Reconnect after backgrounding starts a fresh SSH exec and API process. It does not reuse old handles. The `reconnect` request carries `target`, `expected_target`, `previous_attachment_generation`, `attachment_id`, and the last output/reset checkpoint. `expected_target` contains the stable identity returned by the old process: hub, owning host/config generation, workspace kind/id, tmux session/pane and server incarnation, and stable target generation. The new process resolves the target itself and exact-matches every field. The old output/reset checkpoint is informational because output sequences are process-local and reconnect never replays input; both values may be zero or omitted when the old process returned `opened` but disconnected before its first frame. On success `reconnected` returns a new target and attachment handle, a new API instance, and attachment generation `previous_attachment_generation + 1` before a fresh reset-generation-1 full frame. Reconnect is view-only and never replays input.

Outbound responses use a bounded queue. If the peer stops reading or the writer fails, the service enters a terminal state, revokes attachments, and exits; it does not accept later mutations after a missing acknowledgment.

The canonical synthetic terminal transcript and catalog query/response corpus, with their SHA-256 manifest, live under `testdata/mobile-protocol/v0`. `scripts/mobile-service-proof.sh` builds a temporary binary, creates a private tmux socket and isolated Sidecar state/config, and exercises the terminal stream locally or through `ssh -T aerie.local` without changing the installed Sidecar binary or default tmux server.

## Catalog and attention events over SSH

Native clients can open a separate SSH exec without a PTY running `sidecar api events --stdio`. It bridges the running API service's Local events socket and writes the same `api_version`, `type` and `seq` envelopes as [the UI API events stream](ui-api.md#events-stream), one per JSONL line. It requires the always-on API service on that host and reports how to start it when unavailable. It does not change the terminal v0 handshake, envelopes, operation sequences or attachment lifecycle. Each reconnect starts a new event sequence and catalog baseline; no old attention is replayed. Catalog filters match `sidecar mobile sessions --json`. Additive `workspace` messages invalidate project/workspace resources using the same envelope and sequence; clients that only consume catalog/attention can ignore them. The workspace resources and operations are documented in [UI API v0](ui-api.md#project-workspaces-and-operations).

## Reset reasons

A `reset` event's `reason` says why the attachment's reset generation advanced. Clients may branch on it. The set below is the whole v0 vocabulary, declared as `mobileproto.Reset*` constants and listed in `mobileproto.ResetReasons`. A reason is never renamed, and a new one is added to this table before the service emits it. A client that meets a reason it does not know treats it as a reset that revoked control. Whatever the reason, the client replaces its parser with the next full frame of the new reset generation, and every reason except `resize` revokes control.

| Reason | When it fires | What a client does |
| --- | --- | --- |
| `resize` | This client's own `control` or `resize` changed the pane's geometry. The correlated response comes first. Control is kept. | Apply the replacement frame and continue. Further mutations wait until that frame is applied. |
| `geometry_changed` | The pane's size changed without a request from this attachment, usually because another screen or client took the size, or a tmux layout change. This includes a foreign resize that lands after this client's own `resize` or `control` was acknowledged but before a capture at the requested size: the service stops waiting for that size, so the `resize` reset is followed by a `geometry_changed` reset and then a frame at the size the pane really has. | Show the new size. Take control again only on a deliberate user action, since another screen now holds the size. |
| `alternate_screen` | The pane entered or left the alternate screen, for example a full-screen program started or exited. | Wait for the screen to settle, then take control again if the user was typing. |
| `identity_changed` | A capture showed a different pane, session or tmux server than the one this attachment was opened on. A non-retryable `identity_changed` error accompanies it. | Treat the target as replaced. Close the attachment, and resolve or reconnect to the target again rather than reuse it. |
| `presence_timeout` | The client held control but sent no heartbeat or input for 15 seconds, so the service released its geometry lease. | Take control again explicitly when the user next interacts. |
| `presence_release_failed` | The presence expiry above could not conditionally release the lease. A retryable `backend` error accompanies it. | As for `presence_timeout`. |
| `capture_failed` | The capture source died and the target still validates. A retryable `backend` error accompanies it. The service reseeds with a backoff from 250 ms to 5 seconds. If the target is gone instead, no reset is sent and the attachment ends (see the capture failure rule above). | Keep the attachment and wait for the replacement frame. |
| `capture_invalid` | A capture could not be normalized into a frame. A retryable `backend` error accompanies it. | Keep the attachment. The replacement frame arrives with the next capture that succeeds. |
| `frame_too_large` | A normalized frame would exceed the line bound. A retryable `backend` error accompanies it. | As for `capture_invalid`. A smaller geometry avoids it. |
| `output_unavailable` | Writing a frame failed, so the stream is ending. It is sent on a stream that is already closing, so a client rarely sees it. | Expect the stream to end, then reconnect. |


## Negotiated terminal v1

v1 is additive: **envelopes still carry `version: 0`** on SSH stdio and WebSocket. A hello without `capabilities` receives the unchanged v0 capabilities and behavior, including RIS frames, contiguous output sequences, explicit control and lease-gated input. A new client sends a `capabilities` object in its first hello; the hello and later status advertise the server's supported bits. The server enables only the requested bits for that stream. Reconnect opens a fresh stream and negotiates again. Unknown fields are refused. The new bits are `presence`, `reset_free_frames`, `coalesced_frames`, `server_paste`, and `holder_labels`. `coalesced_frames` requires `reset_free_frames`. `changed_row_frames` remains false; screen-model and changed-row frames are deferred to U3.

```json
{"version":0,"type":"hello","request_id":"hello-1","capabilities":{"presence":true,"reset_free_frames":true,"coalesced_frames":true,"server_paste":true,"holder_labels":true},"viewer":{"kind":"ios","label":"iPhone"}}
```

`viewer` is optional and defaults to `{kind:"unknown", label:"Sidecar viewer"}`. Its kind is `tui`, `browser`, `ios`, `cli`, or `unknown`; its label is 1 through 128 UTF-8 bytes, nonblank and without control characters. It is advisory display text, never an authenticated identity or authority. The owning host, including when reached through the hub, negotiates the same requested capabilities. A selected owner that cannot support a requested bit is refused as `unsupported`; v0 owners stay usable by v0 clients.

### Presence request and acknowledgment

One terminal stream may contain several attachments; presence describes exactly the `attachment_handle` named by its envelope, with one independent lease identity per attachment. It uses the same `operation_sequence`, applied reset and applied output checkpoint fences as input. Fitted geometry describes the client's box, not the geometry of the frame it is currently scaling.

```json
{"version":0,"type":"presence","request_id":"presence-1","attachment_handle":"attachment_example","operation_sequence":1,"last_reset_generation":1,"last_output_sequence":1,"presence":{"focused":true,"visible":true,"idle_ms":0,"columns":100,"rows":30}}
```

All five presence fields are required. `idle_ms` is an integer from 0 through 86400000, `columns` from 2 through 512, and `rows` from 1 through 256. A focused, visible viewer competes through `DecideGeometryLease`, the same rule the TUI uses. A viewer that loses focus or becomes invisible releases its own lease immediately. An idle foreign owner is preempted only when this viewer has sufficiently newer input (the existing five-second margin); polling alone cannot repeatedly steal the size. Selecting a terminal or tapping it counts as input: send `idle_ms:0`. Debounce rapidly changing selections and fitted sizes before sending.

The correlated acknowledgment is `type:"presence"`, with the attachment handle/generation, accepted `operation_sequence`, current `output_sequence` and `reset_generation`, and `control:true` only when this attachment holds the size. False is represented by an omitted `control`, as in v0. A presence resize acknowledges first, then emits `reset` with reason `resize`, then the replacement full frame. Further operations wait for that frame. A failed operation does not consume its sequence.

On a single-pane window, an already fitted presence or input transaction renews ownership without issuing `resize-window`. The geometry condition is evaluated inside the same identity and lease guard as the mutation. Idle preemption compares the owner’s advertised idle duration, sampled when its lease token was refreshed, with the active viewer’s idle duration. The five-second margin is not a wall-clock handoff deadline measured from the abandoned viewer’s last input; heartbeat and lease-refresh cadence determine when that evidence becomes observable. Blur and deliberate input need no idle margin.

Heartbeats remain at five seconds and use the same operation/checkpoint fields. With `presence` negotiated, a heartbeat is valid while viewing without control. It may carry a full `presence` object, or omit it to reuse the last accepted presence while increasing idle time by the elapsed server time. The first heartbeat must supply presence if no presence has been accepted. After fifteen seconds without presence, heartbeat or input, an owned lease expires as in v0. The next presence or input can acquire again.

Input with presence negotiated claims outright and delivers the bytes in one owning-service tmux transaction, even when another viewer owns the size. It retains identity, input-mode and sequence/checkpoint validation. It uses the most recently accepted fitted geometry, or the current frame geometry before any presence. Input is never replayed after an uncertain acknowledgment. The explicit `control`, `resize` and `release` operations remain available for tools and legacy clients.

### Holder labels

With `holder_labels` negotiated, the service emits asynchronous `holder` events whenever its observed holder changes, including on an idle pane. They carry the attachment handle/generation and a `holder` object, never a lease token, owner id or PID:

```json
{"version":0,"type":"holder","attachment_handle":"attachment_example","attachment_generation":1,"holder":{"kind":"ios","label":"iPhone"}}
```

An unowned pane uses empty kind and label. A TUI holder is described as `kind:"tui"`, with a host label such as `TUI on aerie`; an unknown owner falls back to an advisory label. Clients use this event for a quiet, fading “sized for …” hint. Labels convey presentation only and must be rendered as text. The events-stream terminal projection can reuse this holder object.

For local terminals, the project Workspaces and global Sessions TUI headers also name a foreign holder. They reuse the holder interpretation used by negotiated terminal streams, cache metadata during the existing lease observation, and render it through one `termpreview` formatter. Their view functions run no holder subprocess. Application focus refits the current viewport even when its fitted dimensions are unchanged and the pane emits no output. Interactive project terminals keep the same background geometry arbitration as Sessions terminals, including when a click switches directly between live panes. Pane IDs are scoped to their tmux socket, including socket path aliases, so a separate outer TUI server never hides or blocks a managed pane with the same ID.

### Full-frame flags and slow peers

A reset-free frame has `frame_kind:"full"` and `reset_free:true`. Its decoded `render_vt_base64` homes the cursor, clears carried rendition, hyperlink, margins, origin and insert modes, and repaints every row with wrap temporarily disabled. It never emits RIS (`ESC c`) or repeatedly toggles alternate buffers. `modes.alternate_screen` still describes the source application. The client keeps its renderer and selection across ordinary full frames; a new reset generation still invalidates the previous checkpoint and requires a replacement full frame. History remains an independent frozen v0-style transcript.

Apply each complete frame at its own advertised geometry, with parser writes, buffer replacement and resize serialized. A captured grid is not a streaming terminal: do not reflow the previous capture into the new geometry. An emulator may reset its buffer at the old geometry before resizing and applying the replacement; restore authoritative mouse modes afterward, and preserve an ordinary same-geometry reset-free frame's selection. A reset invalidates queued frames and selection-restoration callbacks from the previous reset generation; a changed attachment similarly fences old callbacks. Keep the previous displayed screen until a replacement is ready. Fit and paint are separate checkpoints: the presence acknowledgement establishes ownership before the replacement frame is available. A browser must measure fitted geometry from its visible local box at the configured font size, never from a scaled foreign frame or a hidden/zero-size box. The retained previous grid may stay scaled until replacement. When the fitted replacement is painted, clear the scale transform and show normal-size cells; observe delayed renderer dimension changes after hidden-pane transitions so stale scaling cannot survive that paint. Client presentation signals that a terminal is sized locally must follow the painted fit rather than the earlier ownership acknowledgement. These are receiver requirements, not new wire fields or capabilities. Correct CSS cell rectangles alone do not prove normal glyph size: a bitmap renderer must also keep its drawing viewport aligned with its backing canvas dimensions. The browser falls back to xterm's DOM renderer if WebGL loses that alignment, preserving the same frame, fit and input contracts.

A frame with `coalesced:true` is a complete replacement: **output sequence gaps are valid** within the same attachment/reset generation. Reject stale or decreasing sequences; apply the newest complete frame. The server replaces waiting frames before outbound delivery while keeping correlated acknowledgments, reset events and holder events ordered as barriers. A slow peer receives the latest frame, instead of aborting merely because frames accumulate. Control responses remain bounded and an unread stream can still end when their queue fills or the transport deadline expires. Unnegotiated v0 streams retain contiguous sequences and their original overflow behavior.

Terminal WebSockets offer `permessage-deflate` with context takeover. This is independently negotiated by the WebSocket handshake, so clients that do not offer compression retain their existing transport. It changes no decoded protocol bytes and does not apply to SSH stdio. The 8 MiB limit remains a limit on the decompressed message.

### Server-side paste

With `server_paste` negotiated, send `type:"paste"` with the ordinary attachment/operation/checkpoint fields and `data_base64`, standard base64 encoding 1 through 65536 bytes. Send only the pasted bytes: do not add bracketed-paste escape sequences. The owning service loads a private tmux buffer and uses `paste-buffer -p`; tmux decides whether to bracket for the target application and deletes the buffer afterward. Presence clients claim and deliver exactly as input does; without presence, paste requires explicit control. The acknowledgment is `type:"accepted"`. Unsupported input-mode probes (including tmux 3.4's missing bracket-paste probe) remain view-only.

The server validates the original decoded payload's nonempty size bound, then removes every `ESC[200~` and `ESC[201~` marker until none remains, including markers formed when earlier markers are removed. It repeatedly normalizes CRLF to LF after removal until no CRLF remains, including CRLF formed at a removal boundary or by an earlier normalization. Equivalently, a run of CR bytes directly before LF becomes one LF; CR runs without a following LF remain unchanged. This idempotent policy applies to all server-paste clients over SSH stdio and WebSocket and is independent of tmux version. tmux performs its usual LF-to-CR translation on delivery and supplies the only paste boundaries. A marker-only payload that becomes empty is refused as `invalid_request` before geometry or buffer mutation, without consuming its operation sequence or revoking control. Ordinary input bytes and interactive TUI paste retain their existing semantics.

The shared synthetic v1 transcript and SHA-256 manifest live in `testdata/ui-api/v1/terminal.jsonl`. They cover hello, frame flags, presence, holder change, paste, heartbeat and blur. The v0 wire format remains unchanged. The fixture server reconnect transcript retains the target’s current output and geometry, matching the live backend.

Both legacy and negotiated terminal encoder queues have a 16 MiB byte budget, counting the serialized JSONL response including its newline until the writer completes it. This includes an in-flight response. The existing item/control bounds also apply. Coalescing replaces a pending frame only if the replacement fits the byte budget; overflow terminates the stream rather than retaining unbounded terminal data.

Fixture terminal streams implement the same hello negotiation, presence arbitration, holder events, v1 frame flags, input takeover and paste acknowledgment through the terminal backend interface. They echo normalized server-paste bytes and unmodified ordinary input bytes and launch no process; tmux's final newline translation and bracketed-paste boundaries belong to the live backend. Run `./scripts/ui-api-fixture-proof.sh` to exercise both legacy and negotiated clients without tmux.

## Screen requests over the UI API

API clients can separately register their events connection with `uiRequestRelayV1` to receive agent open/layout requests through focused-window presence and an HTTP acknowledgement. This does not add mobile terminal envelope fields or change terminal presence, lease identity, geometry units or operation sequences. Screen viewports are CSS pixels and terminal viewports remain cells. SSH `api events --stdio` stays read-only and does not register a screen viewer. See [focused API viewers](ui-api.md#focused-api-viewers-and-agent-pane-requests).

A UI layout terminal/shell leaf stores the exact tmux session in `session`, with optional untrusted `attachment: {selector, expected_target}` for a distinct catalog candidate. This preference is separate from terminal attachment handles and never grants terminal authority. Clients revalidate its opaque selector and complete TargetIdentity through the current catalog or resolve flow before opening or reconnecting; the layout server does not parse selectors. Multiple candidates in one session remain distinct through layout reads, writes, relay proposals and CLI full-spec carry. Screen relay requests may carry optional `origin.tmuxPane` to select exactly one matching session/pane hint; otherwise duplicate-session leaves decline as ambiguous. `ui_request.origin_pane` identifies that leaf in the pre-proposal tree. Bounds and carry rules are in [the layout contract](ui-api.md#project-content-and-viewer-layouts); terminal envelopes, presence and lease authority are unchanged.
