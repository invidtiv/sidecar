# Sidecar UI API v0

`sidecar api serve` exposes Sidecar's Sessions and terminals to UIs that are not the TUI: the reference web UI in `~/code/sidecar-ui`, embedded components in other apps, and agents and scripts. This document is the wire contract. The plan and the reasoning behind it are in [the Sidecar UI API plan](../plans/active/sidecar-ui-api.md).

v0 is the U0 steel thread. It serves the Sessions catalog and the existing terminal protocol over HTTP and WebSocket, with the transports, guards and pairing that every later version keeps. U1 adds catalog and attention events. U2 adds project workspaces and operations. U3 adds project content, open-pane invalidations and per-viewer layouts. U4 adds focused API viewers that receive agent open/layout requests. v0 changes in place while the API is private, and fixtures and clients move with it.

## Process and discovery

`sidecar api serve` is one long-running, headless process per user. It never starts, stops or restarts the tmux server. It holds one remote-host registry and catalog router for its lifetime, and gives each terminal connection its own protocol broker, which is the same per-stream model `sidecar mobile serve --stdio` uses.

On start it writes `$STATE/api/endpoint.json` with mode 0600. `$STATE` is `config.StateDir()`. It removes the file on clean exit (SIGINT, SIGTERM, or executable replacement). A second `serve` refuses to start while the first is running: the server holds an exclusive lock on `$STATE/api/serve.lock` for its lifetime, the kernel drops the lock if the process dies, and the refusal names the PID recorded in `endpoint.json`. A client that finds an `endpoint.json` whose PID is not alive treats it as no server. Shutdown closes every owned listener before releasing the lock, including listeners whose serving goroutine has not started, so delayed cleanup cannot unlink a successor socket.

```json
{
  "pid": 4242,
  "version": "v1.16.0",
  "api_version": 0,
  "api_instance": "opaque per-process id",
  "started_at": "2026-10-03T18:00:00Z",
  "unix_socket": "/…/api/api.sock",
  "tcp": "127.0.0.1:7861",
  "tailnet_socket": "/…/api/tailnet.sock"
}
```

`tailnet_socket` is present only when `--tailnet` is given, and `tailnet_tcp` (for example `"127.0.0.1:7862"`) replaces it when `--tailnet-port` is given. CLI verbs and local SDK users discover the server from this file.

The process decides once, at start, whether terminals and the catalog route through the remote-host hub (the `sidecar_remote_hosts` feature with at least one registered host) or through the local owner service. Registering the first host, or removing the last one, takes effect at the next `serve`.

## Listeners and trust

All three listeners serve the same routes. They differ only in how a caller is trusted.

| Listener | Address | Caller is trusted when | Guards |
| --- | --- | --- | --- |
| Local | Unix socket `$STATE/api/api.sock`, mode 0600 | Always. File permissions limit it to the user, the same trust as the tmux socket. | None. Pairing codes, origin management and the bulk browser sign-out are served only here. |
| Browser | TCP `127.0.0.1:<port>`, default 7861, `--port 0` picks a free port | It carries a bearer token (a browser session token or a paired origin's token) or a ticket, bound to the request's origin | Host, Origin and mutation guards |
| Tailnet | Unix socket `$STATE/api/tailnet.sock`, mode 0600, proxied by `tailscale serve unix:<path>` | The `Tailscale-User-Login` header names an allowed login. The header is honored only on this listener. | Host, Origin and mutation guards |

`serve` never binds a non-loopback address in v0.

Under `sidecar api service`, the service manager holds the Browser port continuously, including while the process exits on a binary change and waits to restart. Another local OS user cannot bind that trusted origin during the restart window. This protection lasts while the supervisor retains the listening socket: explicitly stopping, uninstalling, or reinstalling the manager's socket definition frees the port. Foreground `api serve` binds its own port and still has an origin-takeover window after exit; persisted browser credentials must not be treated as safe against another local user serving a page at that origin while it is free. `brew services` provides socket activation on macOS; on Linux use `api service install`.

`serve` adopts manager listeners before binding any missing ones. launchd supplies entries named `browser`, `local`, and optionally `tailnet` through `launch_activate_socket`; systemd supplies descriptors starting at fd 3 with `LISTEN_PID` equal to this process and `LISTEN_FDS` (optional colon-separated `LISTEN_FDNAMES`, plus the optional Linux `LISTEN_PIDFDID` process identity check). Names may be the listener role, empty, or the generated socket unit's shared `sidecar-api` name. Descriptors must be stream sockets with an IPv4 or Unix kernel family; IPv4-mapped IPv6 descriptors are refused. The server classifies each descriptor by its exact address before assigning trust: Browser is `127.0.0.1:<port>` (an inherited port is accepted with `--port 0`), Local is exactly `$STATE/api/api.sock`, and Tailnet must match the explicitly configured socket or fallback port. Unix sockets must already have mode 0600. One exception to classifying by exact address: launchd on current macOS binds an activated Unix socket in its private directory and moves it to `SockPathName`, so the descriptor reports the bind-time path. A descriptor launchd names `local` (or `tailnet`, when the Tailnet socket is enabled) whose address is not the expected path is accepted only after a random token dialed to the expected path arrives on that very descriptor; a client queued before startup is given 250 ms to be that probe and is otherwise closed, and the probe as a whole has two seconds. A named descriptor that the expected path does not reach is refused. Unknown, duplicate, wrong-address or contradictory named descriptors are refused. Inherited Unix sockets are never unlinked on shutdown. Tailnet descriptors are refused unless Tailnet is enabled. Without inherited descriptors, foreground serving binds all listeners as before. Managed definitions set `SIDECAR_API_SOCKET_ACTIVATION=1`, which refuses startup if the Browser listener is missing rather than silently opening a restart window.

With `--tailnet`, `serve` creates the tailnet socket and prints the `tailscale serve` command that exposes it. It does not change the Tailscale configuration itself. Allowed logins come from config `api.tailnetLogins`. If that is unset, the default is the login that owns the local Tailscale node (`tailscale status --json`). If `tailscaled` cannot open a 0600 user socket, as can happen with a sandboxed Tailscale build, the fallback is `--tailnet-port N`: the Tailnet listener, with the same guards, on a dedicated loopback port for the proxy to target (`tailscale serve --bg http://127.0.0.1:N`). That fallback is weaker, and `serve` prints a warning when it is used. The Tailnet listener trusts `Tailscale-User-Login` because only `tailscaled` can reach its 0600 socket, but any local process or OS user can connect to a loopback port, send an allowed login and the MagicDNS `Host`, and drive terminals. A browser cannot do this, because it cannot set that header or that `Host`. Use the fallback only on a machine where every local user and process is already trusted. `serve --tailnet` prints both commands. `serve` cannot detect the failure itself without changing Tailscale configuration, which it never does.

Recorded on aerie on 2026-10-03: the standalone Tailscale build 1.102.4 (`io.tailscale.ipn.macsys`), whose network extension runs as root. Whether it can open the 0600 socket under `~/.local/state/sidecar/api/` is not yet verified, because the U0-a proofs do not change Tailscale configuration. The first live `tailscale serve unix:` run settles it. If it fails, use `--tailnet-port`.

Set `api.tailnetHTTPSPort` to a dedicated Tailscale Serve HTTPS port (for example `7861`) when the node's standard HTTPS route already serves another application. Then use `tailscale serve --bg --https=7861 unix:<path>`. This changes only the Tailnet listener's public Host/Origin guards, not its local Unix socket or the Browser bind. With a nonstandard port configured, only `https://<magicdns>:<port>` is an own origin and only `<magicdns>:<port>` is an allowed Host; the standard ports are no longer trusted on that listener. Zero or `443` preserves the existing standard-port behavior. Login authentication and mutation guards remain required.

For a sandboxed proxy that cannot open the Tailnet Unix socket, `api.browserProxyOrigin` can declare one exact HTTPS origin on the existing Browser listener. For example, set it to `https://aerie.tail53fd54.ts.net:7861` and proxy with `tailscale serve --bg --https=7861 http://127.0.0.1:7861`. Only that additional Host and Origin are accepted; localhost guards remain unchanged. This is Browser authentication: the UI and pairing page can load without a credential, but API requests still require an origin-bound browser bearer and WebSockets require a single-use ticket. Tailscale identity headers are ignored. Open the UI at that origin in the remote browser: it asks for access and shows a code, which you approve from the TUI, a signed-in browser or `sidecar api approve CODE` (see Approving a new browser). Alternatively run `sidecar api open --proxy --print` on the server (or over an existing SSH connection) and open its private one-use link in the remote browser within 60 seconds; keep the link out of chats and logs. Either way this registers one browser rather than automatically granting access to the tailnet node owner. Existing localhost registrations remain valid, but the HTTPS origin requires its own registration.

### Guards on the Browser and Tailnet listeners

- **Host:** the `Host` header must exactly match an allowed value. For Browser that is `127.0.0.1:<port>` and `localhost:<port>`. For Tailnet with the default HTTPS port, it is the node's MagicDNS name (from `tailscale status --json`), bare or with `:443` or `:80`; with a dedicated `api.tailnetHTTPSPort`, only `<magicdns>:<port>` is allowed. Any other value gets `421 host_refused`, on every route including the terminal upgrade. This defeats DNS rebinding.
- **Origin:** a WebSocket upgrade must carry an allowed `Origin`, and so must any request that is not `GET` or `HEAD`, with one exception on the Browser listener: a request or upgrade that carries `Authorization: Bearer <token>` with a non-empty token may omit `Origin` (see Authentication). Any other `Authorization` scheme, such as `Basic`, or an empty bearer token does not qualify, because a browser can attach those by itself. Allowed origins are the listener's own origins plus paired origins. A listener's own origins are `http://127.0.0.1:<port>` and `http://localhost:<port>` for Browser, and `https://<magicdns>` and `http://<magicdns>` for Tailnet with the default port, or only `https://<magicdns>:<port>` with a dedicated HTTPS port. Any request that carries an `Origin` outside that set, including a `GET`, gets `403 origin_refused`. A `GET` or `HEAD` without an `Origin` goes on to authentication.
- **Mutations:** a non-GET request must be `Content-Type: application/json` and must carry `X-Sidecar-Request: 1`. A browser cannot send either cross-site without a CORS preflight, and the server refuses unpaired preflights.
- **CORS:** only paired origins get CORS headers: the exact `Access-Control-Allow-Origin` with `Vary: Origin`, and on a preflight `Access-Control-Allow-Methods: GET, HEAD, POST, PUT, DELETE`, allowed headers `Authorization, Content-Type, X-Sidecar-Request, If-Match, If-None-Match` and exposed response header `ETag`, and `Access-Control-Max-Age: 600`. There are no credentials. A preflight from any other origin gets `403 origin_refused`.

### Authentication on each listener

- **Local:** every request is trusted.
- **Browser:** `/api/` routes need `Authorization: Bearer <token>`, where the token is either a browser session token (see Pairing) or a paired origin's token. Nothing ambient travels with a request: every client, same-origin, paired or non-browser, takes this one path. Each token is bound to one origin. A session token is bound to the exact origin that exchanged its pairing code (for example `http://127.0.0.1:7861`, not also `http://localhost:7861`), and a paired origin's token to that origin. A request that carries any other `Origin` gets `403 origin_refused`. A request with no `Origin` is accepted with a valid bearer token, for any method and on the terminal upgrade, because the Origin guard exists to stop a page from using a credential the browser attaches by itself, and a bearer token is never attached by itself. That covers a same-origin `GET`, curl, Node (whose `WebSocket` sends no `Origin`) and native clients. Without a bearer token, a mutation or upgrade with no `Origin` is still refused, and so is a ticket presented with no `Origin`, because a ticket is bound to its origin. The Tailnet listener keeps requiring `Origin`: its login header is added by `tailscale serve` to every request from the device, so it is ambient. Static UI files, `GET /pair`, the pairing exchange, the two session-proof routes, `POST /api/v0/pairing/requests` (asking for access) and `GET /api/v0/pairing/requests/{id}` (polling that request with its own secret) need no bearer credential. An API route without one gets `401 unauthenticated`.
- **Tailnet:** every route, static files included, needs a `Tailscale-User-Login` header that names an allowed login. A missing login gets `401 unauthenticated`, and a login that is not allowed gets `403 tailnet_login_refused`. The header is ignored on every other listener. The login is ambient (`tailscale serve` adds it to every request from the owner's devices, whatever page sent it), so it authorizes only the listener's own origins and same-origin requests without an `Origin`. A request whose `Origin` is a paired origin must also carry that origin's own `Authorization: Bearer <token>`, and its WebSocket upgrades must spend a ticket bought with that token on this listener; the login alone gets `401 unauthenticated` or close `4401`. Its streams then belong to the paired origin, so revoking or re-pairing it closes them. Browser session tokens are not accepted here.

### Per-client limits

A client is one credential holder: a browser session, a paired origin, or a tailnet login. Each may hold at most 16 open events WebSockets and, separately, 16 open terminal WebSockets (the 17th closes with `4429` and a reason) and 16 unredeemed tickets (the 17th request gets `429 too_many_outstanding`). Redeeming or expiring a ticket frees its slot. Across all clients there are at most 256 unredeemed tickets and 64 unused pairing codes. Access requests have their own limits, listed under Pairing. Local callers are trusted like the tmux socket and have no terminal limit. HTTP content and tree reads share a separate limit of four in-flight requests per credential holder across all projects, including the trusted Local caller. A fifth read gets `429 too_many_outstanding` immediately, without starting or queueing backend work; completion, errors and cancellation free the slot. Layout reads do not spend this budget. File searches have their own separate four-request budget per credential, so loading content panes cannot starve the finder.

## Pairing

A browser gets in one of two ways, and both end with the same thing: a public-key registration in `sessions.json` for that browser's own non-extractable key and its exact origin, renewed into short-lived bearers by the session-proof algorithm below.

- **Approval (the general path).** A browser with no usable registration asks for access and shows a six-character code. Someone already trusted types that code: in the TUI's approval modal, in a signed-in browser, or as `sidecar api approve CODE` on the host. This works on every Browser-listener origin, including `api.browserProxyOrigin`.
- **The pairing link (the host's convenience and recovery path).** `sidecar api open` opens a single-use, 60-second link in the host's own browser, which registers it in one step. It is also the way back in when no trusted surface is at hand.

The host's own localhost browser is not trusted automatically: other local OS users and processes can reach loopback too.

### Approving a new browser

The SDK owns this sequence; a UI renders its states (`requesting`, `waiting {code, expires_at}`, `approved`, `denied`, `expired`).

1. Generate the browser key exactly as the pairing page does: `crypto.subtle.generateKey({name: "ECDSA", namedCurve: "P-256"}, false, ["sign", "verify"])`, non-extractable. Keep it for the life of the request and beyond; it is the key the registration will name.
2. Ask for access: `POST /api/v0/pairing/requests` on the Browser listener, with no bearer, the listener's own exact `Origin` (the same rule as `/pairing/exchange`; a paired origin gets `403 origin_refused`), `Content-Type: application/json` and `X-Sidecar-Request: 1`. Body:

   ```json
   {"public_key":{"kty":"EC","crv":"P-256","x":"<32-byte base64url>","y":"<32-byte base64url>"},"label":"Safari on macOS"}
   ```

   `public_key` follows the exchange's validation (private `d` refused; `key_ops` and `ext` accepted and discarded). `label` is optional: a device name the browser suggests for itself. The server drops control and format characters (including bidirectional overrides), collapses whitespace and caps it at 64 characters, and approvers see it quoted as a claim, never as proof. The server records the request's origin and the TCP peer address itself. Success, `200`:

   ```json
   {"request_id":"<id>","poll_secret":"<secret>","code":"K7Q-4MX","expires_at":"<UTC, 5 minutes away>"}
   ```

   `code` is six Crockford base32 characters in display form. Show it large and copyable. `poll_secret` is returned only here; keep it in page memory. Nothing in this response, or anywhere else in the flow, is a credential.

   Refusals: `400 invalid_request` (bad JSON or key), `403 origin_refused`, `403 mutation_refused`, `421 host_refused`, `403 not_served_here` (Local or Tailnet), `429 too_many_outstanding` (the same browser asked again less than a second after its pending request; retry after a second). Capacity never refuses a request; see Limits.
3. Poll: `GET /api/v0/pairing/requests/{request_id}` with `Authorization: Request <poll_secret>`, every two seconds or so. It needs no bearer and no `Origin`; an `Origin` that is present must be the request's own. Success, `200`:

   ```json
   {"status":"pending","expires_at":"<UTC>"}
   {"status":"approved","expires_at":"<UTC>","registration_id":"<64 hex>"}
   ```

   `status` is `pending`, `approved`, `denied` or `expired`. An unknown id, a wrong or missing secret, another origin, and a request the server has forgotten are all `404 access_request_not_found`, indistinguishably. A settled request (approved, denied or expired) stays answerable for five minutes; a server restart forgets every request.
4. On `approved`: store the IndexedDB record exactly as the pairing page does (`sidecar-browser-auth` v1, store `keys`, key `active`, value `{registration_id, origin, privateKey, publicKey}`), with the `registration_id` from the poll (it equals the digest described under renewal), then run the renewal algorithm to get a bearer.
5. On `denied`, `expired` or `404`: offer a fresh request. `expired` also means the request was evicted to make room (see Limits); ask again. Asking again with the same key replaces that browser's earlier pending request rather than adding one, at most once a second; asking after a restart simply creates a new one.

**Approving.** These routes are for approvers only: the Local socket (the CLI and the TUI), a browser session, and an allowed tailnet login. A paired origin, on any listener, gets `403 approver_refused`; it is an embedding app with its own token and never lets another browser in. On Browser and Tailnet the usual bearer or login authentication and mutation guards apply first. Approve, deny and device revocation decide admission again after the request body has arrived, under the same lock revocation takes: a credential revoked while its request was in flight gets `401 unauthenticated` and changes nothing. Every non-stream request must deliver its body within 10 seconds of its headers, or the connection is closed; the terminal and events streams are exempt.

- `GET /api/v0/pairing/requests` returns pending requests, oldest first, never their codes: `{"requests":[{"request_id","label","origin","address","created_at","expires_at"}]}`. Selecting a row is context only; nothing approves without the code. Behind a proxy every request shows the same address, so requests can look identical: whenever more than one is pending, approval surfaces say so plainly ("2 browsers are waiting; make sure the code is the one on your screen"). The TUI modal and `sidecar api requests` show it before approval, and `sidecar api approve` repeats it after.
- `POST /api/v0/pairing/requests/approve` with `{"code":"K7Q-4MX"}` approves the pending request whose code matches. Matching ignores case, hyphens and spaces, and reads `O` as `0` and `I` or `L` as `1`. It creates (or refreshes) the registration for exactly that request's public key and origin, with the request's label, and returns `{"request_id","registration_id","label","origin","address","approved_via","approved_at"}`. It issues no bearer, ticket or link. `surface` (`"cli"` or `"tui"`) is accepted only on Local, where it names the local surface; elsewhere it is `400 invalid_request`. Refusals: `400 invalid_request` (not a six-character code, which does not count as a wrong code), `404 access_code_invalid` (no pending request has that code), `429 too_many_attempts` (five wrong codes in a minute from this approver; every attempt, right or wrong, is refused until the window passes).
- `POST /api/v0/pairing/requests/deny` with `{"request_id":"<id>"}` denies one pending request and returns `{"request_id","status":"denied"}`; `404 access_request_not_found` when it is not pending.

`approved_via` on the registration is `link` (the pairing link), `cli`, `tui`, `browser:<registration_id>` (the approving browser's registration) or `tailnet:<login>`.

**Limits.** At most 16 pending requests in total and 2 per peer address. A new request is never refused for capacity: when its address already has 2 pending, or the server has 16, the oldest pending request in that bucket is evicted, and its browser's poll reports `expired` (the SDK asks again). Someone nearby can race a request in alongside yours, and the code is what tells them apart; they cannot shut everyone else out by filling the limit. A browser that keeps asking with the same key is limited to one replacement a second (`429 too_many_outstanding`). Through `api.browserProxyOrigin` (or any local proxy) every request has the proxy's loopback address, so all of them share one per-address bucket and show the same address to approvers. Requests expire 5 minutes after creation. Wrong codes are limited to 5 per minute per approver (one approver is one credential holder; Local callers share one budget). At most 64 settled requests are retained for polling.

**Signals.** A new request emits `access_requested` on approvers' events streams (see Events stream) and posts one Sidecar notification with `source: "access_request"` through the shared notification store, so the TUI, `sidecar-ui` and native delivery show it with no extra channel. A burst of requests coalesces into that one notification. It is withdrawn (dismissed) when no request is pending any more, whether by approval, denial or expiry, and on server shutdown; a server that starts dismisses any left by one that died. Its title is `A browser is asking for access` and its body names the claimed label, address and origin but never the code. It carries no targets, and the shared notification rules give it no calls to action: activation means approval. Activating it opens the approval surface: the TUI's modal, or `sidecar-ui`'s approval dialog. A paired origin never sees it: notification reads, events snapshots, claims and receipts omit it for `origin:` callers, and read or dismiss of its id is `404` (a batch skips it).

### Devices

Every registration is a device. Approvers list and revoke them.

- `GET /api/v0/pairing/sessions` returns `{"devices":[{"id","origin","label","approved_via","approved_at","created_at","last_used_at","expires_at","current"}]}`, most recently used first. `id` is the registration ID. `current` is true for the calling browser's own registration.
- `DELETE /api/v0/pairing/sessions/{id}` revokes one registration exactly as the bulk revocation does for many: it is purged from the store before success, its memory bearers get `401`, its challenges and unused tickets stop working, and its terminal and events streams close with `4401`. Returns `{"id","revoked":true,"terminals_closed":N}`; `404 device_not_found` for an id that is neither stored nor holding streams. A browser may revoke itself. Revoking a device does not revoke the devices it approved; `approved_via` shows which device approved each one, so revoke those separately if needed.

### Pairing link: the host's browser and recovery

1. `sidecar api open` asks the server for a single-use pairing code over the Local socket (`POST /api/v0/pairing/codes`). It expires after 60 seconds.
2. `api open` opens `http://127.0.0.1:<port>/pair#code=<code>&next=<path>` in the default browser. `--print` prints the URL instead. The fragment never travels in a request line or `Referer`.
3. `GET /pair` serves the built-in pairing page. Loading it consumes nothing. It has `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, and a CSP allowing only its hashed script and same-origin fetch, with framing forbidden.
4. The script removes the fragment from history, clears the legacy `localStorage` key `sidecar.session`, and generates `crypto.subtle.generateKey({name: "ECDSA", namedCurve: "P-256"}, false, ["sign", "verify"])`. The private key is non-extractable. It exports only the public JWK and sends the code, public key and `next` to the exchange.
5. After success, the page commits an IndexedDB transaction in database `sidecar-browser-auth`, version 1, object store `keys`, key `active`. Its value is `{registration_id, origin, privateKey, publicKey}`; the two keys are structured-cloned `CryptoKey` objects. It stores no bearer. It checks the destination is same-origin and navigates to `next`; the exchange's short-lived bearer is discarded with that page.

`POST /api/v0/pairing/exchange` is Browser-only and accepts only the listener's own exact `Origin`, with `Content-Type: application/json` and `X-Sidecar-Request: 1`. A paired external origin gets `403 origin_refused`; it uses its own origin token. `code` and `public_key` are required; `next` is optional:

```json
{"code":"<fragment code>","public_key":{"kty":"EC","crv":"P-256","x":"<32-byte base64url coordinate>","y":"<32-byte base64url coordinate>"},"next":"/"}
```

Success, `200`:

```json
{"token":"<memory-only bearer>","registration_id":"<public registration ID>","expires_at":"<UTC time, at most 15 minutes away>","next":"/"}
```

The server validates the public P-256 point; private JWK fields such as `d` are refused. WebCrypto's public `key_ops` and `ext` fields are accepted and discarded. `next` defaults to `/` and must start with exactly one `/`, with no scheme, host, backslash or control character. Invalid keys or paths get `400 invalid_request` without consuming the code; an unknown, used or expired code gets `401 pairing_code_invalid`.

### Renewing a browser session: the SDK algorithm

On each page load, after a server restart, and before reconnecting streams, clear `localStorage.removeItem("sidecar.session")`, read `keys["active"]` from IndexedDB, and require its `origin` to equal `location.origin`. Never persist the bearer in localStorage, sessionStorage, IndexedDB, a URL, or a cookie. Keep it only in the page's memory.

1. Send `POST /api/v0/pairing/session-proof` with `{registration_id}`. It needs no bearer, but requires the exact own-origin header and normal mutation headers. The response is `{nonce, timestamp, expires_at}`. `timestamp` is the server's integer Unix time in milliseconds; copy it verbatim. The nonce expires after 60 seconds and is consumed by the first verification attempt, including a refused attempt.
2. Encode these five lines as UTF-8, joined by LF with no trailing newline: `sidecar-browser-session-v1`, `location.origin`, `registration_id`, `nonce`, and the decimal `timestamp`. Sign with `crypto.subtle.sign({name: "ECDSA", hash: "SHA-256"}, privateKey, bytes)`. Use WebCrypto's 64-byte P-256 signature, raw big-endian `r || s`, encoded as unpadded base64url; do not use ASN.1 DER. The signature format follows the [Web Crypto specification](https://www.w3.org/TR/webcrypto/#ecdsa-operations).
3. Send `POST /api/v0/pairing/session-proof/verify` with `{registration_id, nonce, timestamp, signature}` and the same mutation headers. Success returns `{token, expires_at}`. Keep this **15-minute bearer** in memory, send `Authorization: Bearer <token>` for HTTP requests, and buy a new single-use ticket for each WebSocket.
4. Renew before `expires_at`, on reconnect, or once after `401 unauthenticated`; serialize renewal per page to avoid overlapping retries. Do not replay a mutation whose result is uncertain. Renewal issues another independent bearer and leaves other tabs and existing tokens valid until their own expiry. If a challenge or verification gets `401 session_proof_invalid`, discard the inactive registration and start an access request (see Approving a new browser); do not retry a consumed nonce. Network failure may be retried with a fresh challenge.

The registration ID is the lowercase SHA-256 hex digest of `origin + "\n" + public_key.x + "\n" + public_key.y`, using the exact canonical origin. It is a public identifier, not a credential. There may be 16 unused challenges per registration and 64 in total, and 4,096 unexpired in-memory browser bearers; exceeding a limit gets `429 too_many_outstanding`. Codes, challenges, bearers and unused tickets are process-local.

### Persistence, expiry and revocation

`$STATE/api/sessions.json`, mode 0600 beside `origins.json`, contains `{version:2, registrations:{<id>:{public_key, origin, label, approved_via, approved_at, created_at, last_used_at, expires_at}}}`. It stores public keys, exact origin bindings and the device record (the label the browser claimed, how and when it was approved), never a browser bearer, bearer hash or private key. A version-1 store, which lacked the device fields, is migrated in place on first open: every version-1 registration came from a pairing link, so it gets `approved_via: "link"`, `approved_at` equal to `created_at` and an empty label. A Sidecar build older than version 2 refuses a version-2 store as corrupt; move it aside to downgrade. Successful bearer use or signed renewal refreshes last-used time and a **30-day sliding registration expiry**, capped at **180 days from creation**. Refresh writes occur at most once per minute per registration. Existing WebSockets may finish; bearer and registration expiry are enforced on subsequent requests, ticket issuance and stream admission. At 1,024 registrations, pairing evicts the oldest created one and drops its in-memory bearers. Revocation purges matching bearers even if their registration was already evicted; registering the same public key later never revives those old credentials. Pairing or approving a new key leaves existing tabs' registrations valid. Approving a key that is already registered refreshes its label (when the request carried one), `approved_via` and `approved_at`.

Requests use a cached public-key index, reloaded when the store inode, mtime, size or permissions change; unknown bearers are refused before any session-store filesystem work. Writers reload under an exclusive lock on `sessions.json.lock` and atomically replace the 0600 file. CLI revocations go through the Local socket and the admission/revocation lock; the file lock also serializes concurrent store writers. A malformed, oversized or invalid store refuses startup with its path and recovery instructions. Runtime corruption refuses authentication and logs that message. Move the file aside, restart and pair again. Broader file permissions are tightened on read. A legacy bearer-hash store is discarded on startup with a clear re-pair message; the built-in page and updated SDK must clear legacy browser tokens.

`sidecar api devices revoke ID` (`DELETE /api/v0/pairing/sessions/{id}`) removes one registration, as described under Devices. `sidecar api pair --revoke-sessions` (`DELETE /api/v0/pairing/sessions`, Local only) removes all public-key registrations; `--origin URL` (`?origin=URL`) limits it to that exact origin. It invalidates their memory bearers, challenges and unused tickets, and closes their terminal and events streams with `4401`, including older streams whose registration was evicted. `revoked` counts stored registrations; `terminals_closed` counts affected terminals. Purging the store completes before success, so restart cannot restore revoked access. Paired-origin tokens survive this sign-out; `--revoke URL` also purges browser registrations on that origin.

Non-extractable keys prevent ordinary WebCrypto export of private key bytes. They do not authenticate the server. A different local OS user can bind the same loopback port while Sidecar is stopped and serve code on the browser's previously trusted origin. That code can ask the stored key to sign and can steal a short-lived bearer. CryptoKeys are [serializable objects](https://www.w3.org/TR/webcrypto/#cryptokey-interface), so hostile code can clone an opaque key. A clone held at a foreign origin still cannot redeem Sidecar's challenge or reach `/verify`: the browser sends that foreign `Origin`, and the server requires both the listener's own origin and the registration's exact origin binding, even when the signature covers the original origin. The residual danger is a persistent **same-origin** browser context, such as a hostile page or worker, that retains a signing capability after the original page closes. Private key bytes remain non-exportable; cross-origin cloning alone does not grant API access. Revocation or expiry terminates the registered capability. This protocol reduces bearer theft at rest and does not eliminate origin takeover or persistent same-origin misuse.

### Another origin (an embedding app)

`sidecar api pair --origin https://app.example:5173 [--scope SCOPE | --scopes LIST]` registers the origin over the Local socket (`POST /api/v0/origins`) and prints a bearer token. Registrations persist in `$STATE/api/origins.json` with mode 0600, as `{origin, token_sha256, scopes, created_at}`. The server keeps only the token hash. `sidecar api pair --list` lists registrations. `sidecar api pair --revoke ORIGIN` (`DELETE /api/v0/origins?origin=…`, Local only) removes the registration, invalidates its unused tickets, and closes every terminal authenticated with that origin's token or tickets with `4401`. A concurrent request authorized before revocation cannot issue a new ticket or register a terminal afterward. Re-pairing the same URL does not revive the old credential or its tickets. Revoking an origin also purges browser sessions bound to that exact origin, invalidates their tickets and closes their streams. Other origins and their browser sessions remain valid.

`--scope` is repeatable; `--scopes` takes a comma-separated list. Both options may be combined; duplicate scopes are removed. The scopes are `full`, `workspace:write`, `content:read` and `ui:control`. `ui:control` grants screen presence, open/layout delivery and acknowledgements, and the holder's own layout preferences; content bytes still require `content:read`. `workspace:write` grants project workspaces, workspace operations and workspace invalidations. `full` implies every scope. `content:read` grants project content, tree, file search, content invalidations and that credential holder's own layout preferences. It does not grant Sessions, status, terminal access or credential management. Browser sessions, Local callers and allowed Tailnet logins retain full access. Paired-origin scope checks apply equally to bearer and ticket event connections.

HTTP calls from a paired origin send `Authorization: Bearer <token>`. Pairing an origin again rotates its token: the old token, its unredeemed tickets, and every terminal and events stream it opened stop working at once (`4401`), as with revocation. Browsers cannot set headers on a WebSocket, so a paired origin first gets a ticket with `POST /api/v0/ws-tickets` (bearer-authenticated, single-use, 30-second expiry). It then connects with `?ticket=<ticket>`. A ticket is bound to the listener and the origin it was issued to. The same-origin UI does the same with its session token. A non-browser client may instead send `Authorization: Bearer <token>` on the upgrade itself. It either sends no `Origin` or sends the origin that token is bound to (the paired origin, or for a session token the origin that exchanged it); any other `Origin` closes with `4403`.

## Workspace operation core

Workspace writes are prepared for U2 through `workspaceops.Service`, a transport-neutral service with no viewer, selection, or in-flight operation state. The CLI, project Workspaces TUI, and global Sessions view use the same local operation boundary; remote mutations call it on the owning host through the CLI. U2-a adds no HTTP routes, capabilities, or wire fields.

Worktree creation uses a confirmed `WorktreePlan`: plan, begin (Git execution and recovery journal), identity and configured setup, finalization, then launch. The non-interactive `CreateWorktree` composes the same phases the TUI calls separately for progress and recovery. A partial Git success is journaled even after cancellation. Required journal or setup failures retain the created identity and prevent normal finalization and launch. Retry runs setup against that identity; the TUI retains its explicit open-anyway decision and can finalize before opening. Optional warnings retain each surface's existing presentation policy. Task start remains explicit: the project form starts its linked task; CLI and Sessions link without an additional task-start subprocess during setup.

Fresh shell creation requests `ManagedShellSpec.Allocate`; any caller-supplied session preview is advisory. `workspaceops.Service` allocates the display name and session number from the authoritative manifest, creates tmux, and records the identity while holding shellstate's exclusive cross-process lock. CLI, project Workspaces, Sessions, and API callers use the returned identity for launch and focus. Cold project registration is also locked across processes, so concurrent first creates share one manifest. Registry lock contention refuses after five seconds rather than waiting indefinitely. Generated names skip retained tombstones, used display names, and occupied tmux sessions; a tmux collision from another project or an external writer retries with a fresh number. A fresh request never reconnects to another request's session. Explicit-session retry and cold restore retain reconnect semantics. A failed durable write rolls back only the new session. Fresh allocation gives all tmux work, including waiting for in-process server preparation, one two-second budget after obtaining the manifest lock; timeout returns `shell_create_failed` and releases the lock before bounded rollback. Confirmed new sessions are rolled back if a later probe times out. If `new-session` itself times out after creating the session, a private per-create environment marker proves ownership before cleanup; an occupied session belonging to another creator is preserved. Explicit restore/reconnect does not inherit the fresh allocation deadline.

Create refusals carry a named `ShellCreateError`; the CLI returns exit 5 and `--json` writes to stderr the standard `{error: {code, message}}` envelope. `shell_name_invalid` asks for a valid display name, `shell_name_in_use` asks for another name, `shell_create_failed` includes tmux diagnostics and asks the caller to check tmux and the working directory, and `shell_state` asks the caller to check project state or manifest permissions. HTTP adapters retain these codes rather than reducing them to a generic backend failure. Session-name collisions are retried internally and are not a refusal for otherwise valid distinct creates. This change adds no terminal protocol fields, routes, capabilities, or schemas.

Shell create, rename, delete, and tombstone restore, and worktree display-name rename and deletion, go through that service. Shell persistence and locking live only in `shellstate`; the plugin's `ShellManifest` is a compatibility projection with local revision tracking. Tombstone restore restores a durable shell record without starting tmux; cold session recreation remains the existing `sessionrestore` executor. Worktree launch reconnects an existing session rather than creating another one. No operation restarts the tmux server.

Asynchronous viewer completions carry the requesting project context and are rejected before applying state when that context changes. Durable shell operations retain the original project's adapter; dropping a stale UI reply never writes the next project's manifest or starts a continuation there. Sessions additionally fences changed project configuration and replacement operation dialogs while retaining valid replies across ordinary refresh polls. The completion audit and regression contract are in [Workspace asynchronous completion ownership](workspace-completion-fences.md). This is an internal ownership fix: it adds no HTTP routes, capabilities, schemas, fixtures, or mobile protocol fields.

Create shell/worktree JSON with `--agent` includes `agent_start: {kind, status, error?}`. `ready` means Sidecar positively identified the requested provider as idle or done; `failed` includes the existing agent error code/message and the command exits 1 while retaining the created identity for recovery; `not_started` means Sidecar did not request a provider start (for example an explicit `--run`, disabled shell agent control, or required setup failure). Without `--agent` the field is absent. `acked` describes viewer placement only and never provider readiness. Startup waits for positive provider evidence within its existing caller deadline; a shell that has not consumed queued launch input is not declared an exited provider on an elapsed-time heuristic. A provider observed running and then returning to an idle shell still fails immediately. The local launch adapter also records completion of the exact launch attempt in one pane option after its command returns, so a provider that exits wholly between observations fails on the next inspection instead of waiting for the deadline. Each launch uses a fresh random identity; previous completions cannot fail a later launch. This CLI result addition changes no HTTP route or mobile envelope in U2-a; workspace operation API responses use these same shared wire types and include the optional provider-start outcome.

`workspaceops.AgentLauncher` shares readiness and provider start sequencing, retaining each caller's resolved argv, deadlines, target policy, and error wording. Reconnecting worktree sessions skip shell-readiness waiting. `agentresolve.ResolveTarget` accepts explicit caller context and a target lookup adapter, so headless callers share the CLI's target-required and project/shell scoping rules. `workspacelist.Projected`, `SectionsAt`, the pin helpers, and `Hidden` provide state-free list policy; clocks, pins, and source-resolved visibility facts are caller inputs. Human selection, scrolling, collapsed sections, and presentation remain in their models.

## Project workspaces and operations

U2 serves configured projects and their workspaces. `GET /api/v0/projects` uses the `sidecar project list --json` types (`projects: [{key, name, path, theme?, openIn?, addedAt?}]`, `aligned: false`). Shell/visible project cues belong to the CLI caller and are omitted by the headless API. `?host=ID` reads the owning registered host's CLI; omit it or use `local` for this machine. A project key is the `key` from that owner's projects resource, not the hub-scoped `project_id` in Sessions. Encode the entire project selector as one path segment; an owning root path such as `/remote/repo` is `%2Fremote%2Frepo`.

`GET /api/v0/projects/{project}/workspace` returns `{project, catalog, shells}`. `catalog` is the existing `CatalogSnapshot`, restricted to this project after the shared filtering, sorting and grouping rules; it retains the agent state, attention and attachment verdicts of Sessions. When remote hosts are configured (the hub routes every terminal), each row is the same row `/sessions` serves, with the hub's public IDs, selectors and expected identities, plus the owner's `content_workspace_id` on the row and on each candidate matching by session and pane; the hub strips those and project content needs them. A row the hub does not list stays visible but is not attachable. This applies to `?host=` remote project workspaces too. `shells` is the full `sidecar shell list --json` record list, including `status: "forgotten"` and `deletedAt` for recoverable tombstones. Workspace `catalog.generation` additionally covers those records. Query parameters are `sort`, `search`, repeatable `provider` and `state`, `show_idle_sessions`, and a single owning `host`. Omitted idle preference includes all rows. `sidecar workspace list --project NAME [--host ID] --json` returns this exact resource; filtering never removes recoverable records from `shells`.

Current owning-host producers include `main_checkout` on every workspace catalog row: true only for the project's main Git checkout, false for other worktrees and managed shells. Clients use this fact to hide worktree deletion for the main checkout; the server still enforces the refusal. Local project `path` and catalog row `path` use the same canonical absolute path spelling (symlinks resolved when available). Remote paths remain the owning host's paths, never canonicalized on the viewer. The same `main_checkout` field appears in Sessions, event catalogs, CLI catalogs and mobile catalogs; older producers may omit it, and hubs preserve that absence through relay. Clients treat absence as unknown rather than permission to delete.

Shell and agent operation `target` is a literal exact tmux session name from the resource, including names beginning with `-`, `name:` or `session:`. A vanished identity never falls back to another shell's display name. A bare CLI target first matches an exact session. Ordinary display names such as `rev U3-c` or `Shell 3` still resolve when unique, and refuse when ambiguous. Missing `sidecar-sh-*`, `sidecar-ws-*` and `sidecar-tp-*` targets never fall back to display names. `name:DISPLAY` explicitly requests display-name resolution, including session-shaped display names, and must be unique within explicit project/host scope. `session:NAME` escapes a literal CLI session name beginning with a selector prefix. Shell record restore accepts only literal exact session names. `session restore --shell TARGET` applies the same CLI selector rules to restore records; `--exact-shell` requires a literal exact identity. Cold restore searches the machine's restore records without project scoping, so ambiguous names require an exact session from `session status`. Terminal selectors are exact catalog identities and never use display-name resolution.

API-to-owner commands carry an exact-target parser guard (`--exact-target` for rename/delete/prompt; `agent start --target SESSION` for start). Remote CLI agent session targets use the same guard; ordinary bare and explicit display-name selectors carry `--exact-target=false` so the owner applies the selector rules. Targeted cold restore carries `--exact-shell` for literal identities or `--exact-shell=false` for display-name-capable selectors. Owners without these flags refuse before mutation; upgrade the owning Sidecar before retrying. Shell restore uses `-- SESSION`; agent start uses its explicit target flag and keeps `--` solely as the provider argv delimiter. Prompt `text` is always literal, including exactly `-`, and is never read as a stdin sentinel.

Every operation below is POST under `/api/v0/projects/{project}/`. The request is one bounded JSON object. An optional `host` selects a registered owning host; no remote target is ever resolved or mutated on the viewer. Unknown fields and irrelevant operation fields are refused. Local operations reuse the CLI's explicit-project command adapters over `workspaceops.Service`, `agentresolve` and `agentcontrol.Service`; remote operations invoke the owning CLI through the same host transport Sessions uses. This retains the CLI's target resolution, setup/recovery sequencing and provider refusal policy. Create requests use workspace placement and a zero UI-ack wait, as an agent's `--tab --wait 0` invocation does.

Operations require `workspace:write`; `full` implies it. Local access, the Tailnet listener's own origin and paired browser sessions retain full access. Paired-origin scopes default to `full`; an explicitly scoped credential without `workspace:write` or `full` receives `403 scope_refused` on these POSTs. Pairing accepts `workspace:write` alongside `full`; agents select scopes with `sidecar api pair --origin URL --scope workspace:write --json` (repeat `--scope` for multiple scopes). Workspace reads and invalidations require this same scope. Sessions, status and terminals require `full`; narrower scopes may be combined with `content:read` to add content and layout access.

HTTP success bodies are the shared CLI JSON types, with a trailing newline. `X-Sidecar-Exit-Code` reports the original CLI status and is exposed to paired-origin CORS clients. CLI exit 2 maps to HTTP 400, 3 to 404, 4/5 to 409, and other failures to 503. Named CLI refusal codes are preserved; older commands that emit plain stderr map to `invalid_request`, `not_found`, `refused`, `rejected` or `backend` according to their exit status. Remote result-decoding failures remain HTTP failures even if the CLI exited zero. Remote nonzero exits retain validated stdout creation receipts as well as stderr refusals. Worktree setup/launch failures can carry the CLI's partial creation result with a non-success HTTP status, so the created identity and recovery outcomes remain inspectable. Never infer that a failed response means no work happened.

A `workspace` event carries `workspace: {projects, workspaces: [{project, host?}]}`. It follows the initial catalog/terminal baseline and invalidates the projects resource and each listed workspace; clients refetch only the resources they have open. `projects` replaces the local configured project list, including an empty list after removal; remote references retain the owner's canonical project root and registered host, which the owning CLI accepts as a project selector. A workspace event also invalidates any open remote project/workspace resources, so removed projects and disconnected hosts clear stale views. These events share the existing manifest/configuration/agent/host observation signals and the 250 ms debounce. The pending event is latest-wins, bounded to one resource invalidation per connection. There is no extra fast inventory polling. API writes also signal the same event bus, including record-only restore.

The synthetic projects, workspace, workspace event and operation exchanges are in `testdata/ui-api/v0/`, under the same schema/checksum gate. Fixture workspaces support reads; mutations refuse `unsupported` and never fall through to the machine. `./scripts/ui-api-proof.sh` exercises HTTP/CLI workspace parity, shell create/rename/delete/restore, workspace push, worktree planning/source fencing, dirty confirmation, delete identity fencing and agent-feature refusals with both tmux and state isolated. Unit tests also exercise simultaneous API and TUI manifest writers with the live path watcher.

### Workspace client presentation

The sidecar-ui SDK exposes the generated operation-specific request/response types through `projects`, `workspace` and `workspaceOperation`, and delivers normalized `workspace` invalidations through `Session.events`. Non-success bodies, including partial creation and agent submission receipts, remain available as `SidecarError.result`; the CLI status is `exitCode`. Consumers must preserve those outcomes and must not retry uncertain mutations. The embeddable `<sidecar-workspace>` renders project worktrees, shells and forgotten shell records, with in-context create/rename/delete/restore and agent forms. It renders the exact dirty probe and submits all deletion guards and branch decisions from the plan. Restore is record-only shell recovery; deleted Git worktrees use creation rather than an invented restore route. Terminal opens emit the untouched catalog row or explicit candidate for the host app to place. U2-c added no wire routes or capabilities. The subsequent server safety fix adds `main_checkout` to the shared catalog schema and requires exact shell/agent operation targets.

## HTTP routes

Catalog rows optionally include `path`: the owning workspace path, falling back to its project root. Local catalog rows and their worktree candidates expose optional `content_workspace_id`. Empty or absent selects the configured project root; a nonempty value names the owning linked worktree. Shells and candidates sharing an owning root share this selector, consistently with `path` and relay resolution. It is independent of terminal `workspace_id` and `expected_target`, which retain their existing identity and authority. Never derive a content selector from opaque row IDs, candidate selectors or terminal identities. Hub-remapped remote rows and candidates omit it because these routes serve local projects only; absence on a remote row does not enable local content for that row. Older producers may omit the field; absence does not identify a linked worktree for them.

## Project content and viewer layouts

All three listeners serve these resources. `{project}` is the project's key as `GET /api/v0/projects` reports it, or its exact configured name (URL-encoded); either must identify one configured project, and a selector that matches two projects is refused. There is no current-project default. Reads use `contentservice` and return its existing CLI DTOs with camelCase content metadata intact. Optional `workspace` takes the row or candidate's `content_workspace_id`; empty or omitted reads the configured project root. Legacy durable shell/worktree IDs belonging to that project remain accepted. Shell lookup preserves durable ownership through configured symlink aliases such as `/tmp` and `/private/tmp`; duplicate shell claims across equivalent registrations are refused. Case aliases are equivalent only when the filesystem identifies the same directory, so distinct roots on case-sensitive volumes stay separate. Project registrations pin their resolved root; moving a project and repointing its alias cannot lend its manifest to a different checkout. Legacy registrations are pinned on their next creating resolve without changing the registered spelling; read-only lookup does not write metadata and cannot reconstruct an alias target changed before that adoption. Worktree roots are resolved from current registered Git membership. Remote hub-scoped IDs are refused rather than read as local paths; remote content forwarding is not added in this lane.

Matching ignores case, including Unicode case, and requires every whitespace-separated query term. Each term uses its highest-scoring alignment: basename characters, adjacent matches, segment and word boundaries (`/`, `.`, `-`, `_`, space), camelCase humps, and basename starts earn bonuses; gaps and path depth pay small penalties. The API positions and TUI highlights describe that same alignment, including isolated matched characters. For example, `dsk` on `docs/design/desktop-shell.md` returns `[12, 14, 15]`, all in the basename. Scores are relative ranking values, not a stable numeric contract.

File search uses `internal/filefind`, the same scan, fuzzy matcher and recent boost as the TUI. With an empty query it lists still-present recent files first, then shallow project paths. Dotfiles are findable unless the root `.gitignore` excludes them; common output/dependency directories are skipped exactly like the TUI. Scans additionally enforce the API content boundary, excluding Git administrative paths and escaping symlinks. Recent hints affect ranking only and never authorize a path. The server keeps at most 32 root indexes, each bounded to 50,000 files and a two-second walk. Typing reuses the index. After ten seconds, directory and `.gitignore` timestamps invalidate changed lists; incomplete or unsettled scans are walked again instead of trusted. Root replacement invalidates immediately. `truncated` reports additional ranked matches beyond the result limit; `warning` reports an incomplete scan, such as a count/time limit. Scan waits, walks and ranking stop on client cancellation. Searches use a separate budget of four in-flight requests per credential across projects; a fifth gets `429 too_many_outstanding`. Clients must check hello's `file_search` capability before calling an older server. The non-interactive equivalent is `sidecar files find QUERY --project PROJECT [--workspace ID] [--recent PATH] [--limit N] --json`.

Content routes require `content:read`; layout preferences accept `content:read` or `ui:control`; `full` implies both. Unknown/repeated scalar queries get 400 `invalid_request`. Content JSON uses the same bounded encoder as the CLI (at most 768 KiB, with explicit truncation/oversize flags). Git patches are streamed into a bounded 768 KiB prefix with one byte of lookahead, and Git is stopped and reaped once that bound is exceeded. `diff.truncated` reports omitted patch bytes even when the JSON encoder needs no further clipping. File rows and patch statistics describe only the retained prefix; the total omitted size is unknown. Desktop diff readers share the same bounded core and show a truncation notice. Full-file diffs retain their existing 1 MiB per-file bound and report clipping explicitly in both `diff.truncated` and `fullFile.truncated`. When source content is clipped, `pageTotal` is a lower bound from retained content, rather than the full file line count. Core refusals retain `usage`, `unknown-kind`, `rejected` and `internal` codes, mapped to 400, 400, 403 and 503 respectively. `scope_refused` is 403. No path may be absolute, home-relative, contain a `..` component, or escape its resolved workspace through a symlink. Root-handle file and directory reads retain that boundary during concurrent symlink replacement. Resolved API paths open without following newly substituted links at any component, so an ordinary path cannot be redirected into Git metadata after its policy check. Bare repositories whose project root is the Git administrative directory refuse file and tree reads. Content previews and diffs keep the existing size/paging limits. No file, issue or note write route is added.

API content reads, diffs, tree expansion and content subscriptions refuse Git administrative content with `403 rejected` (subscriptions close with `4400`). This includes `.git` at any path component, a worktree's resolved Git directory and common Git directory, and in-root symlink aliases to them. Project tree listings omit those entries. Aggregate working-tree, range and commit responses exclude protected paths before Git emits patches or statistics and before untracked-file readers inspect or open them. Selected-file diff paths are literal filenames, with the same exclusions applied to patches even when a path denotes a directory; wildcard characters and Git pathspec magic cannot broaden a read. Git config may contain remote URLs with embedded credentials, so this protection applies by default even with `content:read` or `full`. Ordinary project files such as `.env` remain readable and watchable: users may need to inspect them as project content, and granting content access grants access to those files. Desktop file browsing retains its existing behavior. Git patches may include tracked symlink target strings; they do not dereference those links into administrative content. Aggregate subscriptions omit protected alias content watches while retaining Git invalidation. Diff invalidation may internally watch Git administrative files without exposing their contents.

Diff file-row `path` values are decoded repository-relative filenames, without Git's `a/` or `b/` prefixes or C-style quoting. Working-tree, range and commit rows preserve spaces, quotes and non-ASCII names; renamed rows name the destination, and deleted rows retain the source name. Raw patch strings retain Git's patch syntax. Clients can pass an ordinary row path unchanged as a file target or selected-diff path through the API, URL-encoding query values. Aggregate rows may name files containing control characters, but selected content reads and subscriptions continue to refuse those paths with `403 rejected`. Render all filenames as text.

Content clients resolve relative Markdown file links against the loaded document's display path, normalize them into project-relative file requests, and retain the pane's workspace. Each navigation reads through the content API, which revalidates paths and symlink containment. External HTTP(S) links open with `noopener` and `noreferrer`; unsafe schemes and raw markup remain inert. The `sidecar-content-title` DOM event carries `{ref, title}` for a loaded document, issue, note or commit title; it is client-only and adds no wire field or schema. An empty terminal leaf is the existing blank split placeholder: it starts no content read until the user chooses content.

The layout store lives under `$STATE/api/layouts/`, with private directories, mode-0600 JSON and lock files, cross-process read/compare/write locking and atomic replacement. Authentication selects the viewer: one browser session, one paired origin (stable through token rotation), one Tailnet login, or the trusted Local caller. No caller-supplied viewer parameter is accepted. Layout preferences grant no terminal or file authority. Each credential holder and canonical workspace root has its own file; the TUI's state remains separate. Layout GET, HEAD and PUT accept one optional `workspace` query parameter (a durable ID, at most 4096 UTF-8 bytes), using the same project membership resolver as content and viewer presence. Omission or an empty selector uses the configured project root. An explicit main-worktree ID addresses that same preference; a linked worktree has its own preference, and shell IDs resolving to the same root share it. Unknown/repeated query parameters get 400 `invalid_request`; foreign, removed or remote hub-scoped workspaces get 403 `rejected`. Explicit worktree selectors must identify a current checkout at its registered path in the same repository; a stale Git registration does not authorize a missing/recreated directory, an unrelated repository or a substituted symlink. Layouts grant no content authority: saved references remain untrusted, and content reads and relay proposals apply traversal, symlink and Git-metadata checks within the selected root. The store uses the shared `panecodec`/`panelayout` tree vocabulary: `split: {axis: "cols"|"rows", ratio: 15..85, a, b}`, leaves `terminal`, `shell`, `doc`, `issue`, `note`, `diff`, `resource`, and their existing tab arrays. Multiple terminal/shell leaves remain distinct. There is no cell geometry, host/source restore metadata or legacy issue leaf. Bounds are 16 split levels, 127 nodes, 64 tabs per content leaf and a 64 KiB request body. `{layout:null}` clears the preference with the same conditional-write rule. Invalid trees return 400 `invalid_request`; storage failures return 503 `internal`.

Terminal and shell layout leaves use `session` for the exact tmux session name. They may also carry `attachment: {selector, expected_target}`, where `selector` is an opaque catalog candidate selector and `expected_target` is the catalog's `mobileproto.TargetIdentity`. The server preserves these strings unchanged through layout GET/PUT, HEAD's ETag, relay proposals and acknowledgements, raw trees and `ViewerLayoutReport` grid panes. The attachment is client-supplied, untrusted preference data: the server never parses its selector, resolves a terminal with it, or treats it as authority. Before use, clients must revalidate the hint through the current catalog or terminal resolve flow and compare the returned identity. Old layouts with no attachment retain their existing behavior.

An attachment is accepted only on a terminal/shell leaf with a nonempty session. Its selector is 1..512 UTF-8 bytes, its nine `expected_target` strings must be nonempty, and every string must be valid UTF-8 without Unicode control characters, except that `owner_host_id` and `workspace_id` may hold the one unit separator (U+001F) a hub places between a host and its key, with a nonempty side on each, as `/sessions` rows carry them. The compact JSON encoding of the complete attachment is at most 8192 bytes; the existing 64 KiB layout body bound also applies. Invalid attachments return 400 `invalid_request`. The server does not require the hinted session to agree with the leaf session: a stale hint is stored verbatim, but cannot override the authoritative session during relay matching.

Open content panes subscribe on the events URL using repeated `content` parameters, each a URL-encoded JSON `ContentRef`: `{project, workspace?, kind, target?, operation?, path?}`. `kind` also accepts `tree`, whose target is its expanded directory. Up to 32 refs are allowed per socket; each encoded ref is at most 8192 bytes. Each ref owns its own watcher, and a remote credential may hold at most 64 directory registrations across all of its events streams (a file registers its parent directory); a subscription beyond that closes with 4429 and its reason. The bound exists because kqueue spends a descriptor on every entry of a watched directory. For example, `content={"project":"sidecar","kind":"file","target":"README.md"}` watches that document. Reconnect with a new set when panes open, close or navigate, then refetch the open panes to establish a fresh baseline. Watchers are registered before hello, stopped on disconnect/revocation/shutdown, and never attached for closed panes. A content-only origin receives hello and subscribed content invalidations, with no catalog, attention or terminal data.

File watches cover the path and its resolved in-root symlink target; an absent in-root file remains watchable for creation, while a missing child beneath an escaping symlink is refused by a rooted stat; tree watches cover requested directories; issue/note watches reuse the td store-directory targets (including WAL writes). Diff watches cover resolved Git administrative paths and the files already under review, at most 64 directories. Like the desktop diff watcher, they do not recursively monitor every previously clean directory: the first edit there is noticed after a Git operation or a manual refetch. Signals coalesce and pending content batches contain only the latest set of invalidated subscribed refs. There is no content polling clock; a slow 30-second registration check only reattaches known watch targets after directory replacement. Refetch through the matching content/tree route, using revisions if available. Immutable fixture content uses the recorded `content-*.json` DTOs and never falls through to real host content or td.

## Terminal stream

`GET /api/v0/terminal` upgrades to a WebSocket. Each connection is one terminal protocol stream: the [mobile terminal protocol](mobile-protocol.md), with unchanged v0 behavior and capability-negotiated v1 presence, reset-free/coalesced frames, holder labels and server-side paste. Every rule in that document applies, including `hello` first, `operation_sequence`, heartbeats, the geometry lease, `history`, `reconnect`, and the refusal of `sessions` while an attachment is open (use `GET /api/v0/sessions` instead).

- Each WebSocket **text** message carries exactly one protocol JSON envelope, with no trailing newline. The 8 MiB line bound applies per message. A binary message, an empty message, or one that contains a CR or LF closes the connection with code `4400`. A message over the bound closes with `1009`.
- Closing the socket is end-of-stream. The server releases that stream's lease exactly as it does on stdin EOF.
- The server pings every 30 seconds. A peer whose pong does not arrive within 15 seconds is dropped, which is end-of-stream too, so a half-open socket (a laptop that slept, a proxy that lost the peer) cannot hold a terminal or its lease. Browsers answer pings automatically; other clients must keep reading. The server reads a pong only while it is reading the socket, and the protocol service handles requests one at a time, so while the server's own inbound side is blocked handing a request to a busy service it skips the ping and excuses a missed pong. That exemption lasts at most one minute since connection start or the last successful pong, checked on each ping interval. The server then closes the socket, breaks the blocked request write, and cancels the backend, so a peer that disappears during a permanent service stall cannot retain a terminal indefinitely.
- The `Host` guard answers `421` before the upgrade. Every other refusal happens after the upgrade, as a close code, because a browser cannot read the status of a failed handshake.
- Close codes:
  - `1000`: the protocol stream ended normally.
  - `4400`: protocol violation. This includes a stream the service ends right after an `invalid_request`, `protocol_mismatch` or `handshake_required` error, which is delivered before the close.
  - `4401`: unauthenticated: no usable ticket, bearer token or tailnet login, or a used or expired ticket. An open terminal also closes with `4401` when the browser session it was opened with is revoked.
  - `4403`: origin refused: no `Origin` without a bearer token (a ticket alone needs its `Origin`), an origin that is not allowed, or a ticket or token used from another origin.
  - `4409`: the server is shutting down.
  - `4429`: too many terminals: this client already holds 16 open terminal WebSockets (the WebSocket form of `too_many_outstanding`). Close one and retry.
  - `1011`: internal error.

  The close reason is one human sentence of at most 123 bytes.
- When remote hosts are configured, the stream is brokered to the owning host exactly as `sidecar mobile serve --stdio` does. When they are not, it is served by the local owner service in-process.

Unnegotiated v0 inherits the mobile service's bounded outbound queue. Clients that negotiate `coalesced_frames` receive latest-wins full frames while control/reset ordering remains intact. The terminal WebSocket offers `permessage-deflate` with context takeover; clients opt into compression in the WebSocket handshake. See [negotiated terminal v1](mobile-protocol.md#negotiated-terminal-v1) for the exact hello, presence, holder, frame flags and paste contract.

Browser terminal receivers serialize frame application with emulator buffer replacement and resize, apply the frame's advertised geometry, and avoid reflowing a previous captured grid. Reset and attachment changes invalidate old queued paints and callbacks. The previous screen remains displayed until the complete replacement is ready, including during another viewer's presence takeover and the browser's claim back. See [full-frame receiver requirements](mobile-protocol.md#full-frame-flags-and-slow-peers). This clarifies client rendering behavior without changing the wire contract, schemas or fixtures. The fit addon measures the visible local pane at the configured font size, independently of the displayed foreign grid and its transform. Hidden or zero-size panes retain their last valid fit and do not claim a fabricated minimum grid. Once the locally fitted replacement is painted, the browser clears the scale transform and renders normal-size cells filling the pane (with less than one cell of remainder at each edge). Another screen's grid, or the retained grid while a replacement is pending, may still be scaled. A control acknowledgement alone is not evidence that the locally fitted grid has been painted: `<sidecar-terminal>` reports `data-size="here"` and `sidecar-state-change.detail.sizedHere` only after that paint; it reports `pending` during the handoff. Pane activation and the renderer's own asynchronous size changes remeasure or relayout without requiring a window resize. Correct CSS cell rectangles alone do not prove normal glyph size: a bitmap renderer must also keep its drawing viewport aligned with its backing canvas dimensions. The browser falls back to xterm's DOM renderer if WebGL loses that alignment, preserving the same frame, fit and input contracts.

## Expected terminal exit

The HTTP `/hello` capabilities advertise `terminal_ended` before a browser sends that additive capability in its terminal JSONL/WebSocket hello. Clients must omit the new hello field against older servers whose strict request decoder does not know it. When the owner proves a pane process exit, negotiated clients receive `{"version":0,"type":"ended","attachment_handle":"…","attachment_generation":1,"reason":"exited"}` with optional `exit_status` when known. The attachment is final: retain and dim the last screen, stop mutations and reconnect, and close a dedicated WebSocket normally. The server sends no reset or error for that exit, and a multiplexed connection remains usable. Older clients omit the capability and retain the legacy refusal behavior. See [the mobile protocol](mobile-protocol.md) for the exact end and recovery contract.

The tmux control notification wakes a fresh exact-target check, rather than waiting for catalog polling. Disappeared managed sessions on the same live server are conditionally forgotten through the shared manifest store; filesystem invalidation then pushes fresh catalog and workspace resources through the existing debounce. Retained `remain-on-exit` panes keep their recoverable record. Lost or replaced servers preserve cold restore eligibility. The existing `exit-empty: off` server preparation lets the final managed shell use the same positive exit proof.

## Events stream

Credential revocation closes event sockets with `4401`, including sockets opened through a ticket or with a browser session that has since been evicted from the auth store. Revocation interrupts the writer independently of queued events and stalled data writes. If the peer has stopped reading, delivery of the close frame is best-effort and the socket closes within the five-second control-write deadline. Admission rechecks the credential under the same lock as revocation, so an already-authorized upgrade cannot connect after sign-out. `terminals_closed` in a session-revocation response counts terminal sockets only; event sockets close too.

`GET /api/v0/events` upgrades to a server-to-client WebSocket on every listener. Authentication, Host and Origin guards, tickets, keepalive and close codes are the same as the terminal stream. A browser spends a fresh ticket for this socket; tickets remain single-use across both stream routes. A non-browser client can send a bearer token without Origin. Tailnet upgrades still require the allowed Origin and login. This route accepts only GET. After authentication, an invalid query closes with `4400`. Client data messages are refused with `4400`; clients only read and answer WebSocket pings.

Paired origins receive only events their scopes allow: catalog, attention and terminals require `full`; workspace invalidations require `workspace:write`; subscribed content invalidations require `content:read`. `full` implies all three. Hello and shutdown apply to every stream.

Every text frame is one `uiapi.EventMessage` JSON object with `api_version: 0`, `type`, and `seq`. `hello` is first at sequence 1. Workspace and terminal baselines may arrive in either order. Sequence increases contiguously on delivery within this connection and starts again on reconnect. There is no replay cursor: reconnect establishes a fresh catalog and terminal baseline, without replaying old attention.

Negotiated terminal holder events supply `tui`, `browser`, `ios`, `cli`, or `unknown` kinds and the viewer label, as specified in [mobile-protocol.md](mobile-protocol.md#negotiated-terminal-v1). Events project that observed holder without exposing a lease token, control epoch, attachment handle or instance id; an empty holder becomes null. For legacy terminal streams without holder negotiation, the read-only holder adapter supplies `tui` (for example `TUI on aerie`), `api` (`API terminal`), or `mobile` (`Mobile app`), and a missing or unreadable holder is null.

One in-process hostserve observer supplies local invalidations, reusing its shells.json watchers and the same agent activity/status collector desktop Sessions uses. Its observation-only mode never reaps shell records or registers a viewer inherited from the launching shell. Remote changes come from the existing host registry's snapshot/diff updates, including health and incarnation changes. Observation clocks and terminal preview bytes do not invalidate the catalog. Configuration changes refresh the observer's project set. Catalog invalidations coalesce over 250 ms; unchanged generations are never resent. Agent transitions retain hostserve's adaptive 5/10/30-second status cadence, and worktree inventory and degraded watches retain its 60-second reconciliation. There is no fast full-catalog polling loop. Holder observation checks only open attachment leases once per second and after attachment changes; it never captures terminal output or collects a catalog.

Legacy observations are shared across all event streams and credentials by owning host and session, including concurrent reads and null results, and cached for one second after each read completes. The cache holds at most 1024 session observations and permits at most four concurrent adapter reads, each with a two-second deadline. At either bound, a stream retains the last observation (or null until its first successful observation) and checks again on its next refresh; fresh and in-flight entries are never evicted to admit another read. A disconnect cancels only that stream's wait; the shared read lives until completion, its deadline, or API shutdown. Negotiated holder messages remain authoritative and bypass the legacy cache.

Each connection has bounded pending state: latest catalog, latest terminal snapshot, one error, and at most 4,096 attention keys (catalog row id plus attention kind), with a 1 MiB total encoded attention bound. Repeated alerts for a key retain the latest observation. Catalog and terminal snapshots coalesce while a socket is slow; they do not abort on queue overflow. A changing row population that exceeds the attention bound emits an explicit `overflow` error, never silently discards an alert. Sequence is assigned at delivery, so coalescing creates no sequence gaps. A peer whose network write exceeds 15 seconds is disconnected.

`sidecar api events --stdio` bridges this exact Local event stream to JSONL for agents and native SSH clients. The API service must already be running on the SSH target. Run it without a PTY; ending the SSH exec or closing stdout ends only this event connection. Terminal SSH streams remain separate.

The typed transcript is `testdata/ui-api/v0/events-stream.jsonl`; it is checked for event ordering and included in the SHA-256 fixture manifest.

## Focused API viewers and agent pane requests

A client opts its events connection into screen delivery with `GET /api/v0/events?viewer=uiRequestRelayV1`. Only `full` or `ui:control` credentials can register; other scopes receive close 4403. The `viewer` message immediately after hello supplies an opaque connection ID. It is a routing identity, never an authentication credential. HTTP requests still need the same credential holder, Origin and mutation guards; another credential cannot report presence or acknowledge this viewer. Multiple windows under one credential have separate connection IDs and share that credential's U3 layout preference. Reconnecting creates a new ID and never replays a request.

`POST /api/v0/viewers/presence` reports `{viewer_id, focused, visible, project, workspace?, session?, focused_pane?, viewport:{width,height}}` and returns `{holder:true|false}`. Project/workspace resolve through the content backend; there is no ambient project. Width and height are integer CSS pixels, 1..32768, for the pane area, excluding the sidebar and other chrome. `focused_pane` is a nonnegative node number in the displayed layout's deterministic depth-first preorder (root is 1, including splits), or 0 when none is focused. Save the displayed tree through the layout route with the same `workspace` selector before announcing it; displayed terminal leaves carry their exact session and may retain the opaque attachment hint described above. `session` identifies the selected origin terminal; it must also appear in that tree for shell-origin requests. Terminal geometry presence remains independent and keeps its terminal-cell units. Presence and acknowledgements adopt the credential that authenticated them, so a browser that renews its 15-minute bearer keeps its viewer deliverable without reconnecting; revoking the credential still closes the stream and removes the viewer.

The most recent **transition into focused and visible** wins among live, authorized connections. A repeated heartbeat cannot steal from a newly focused window. Send presence on focus, blur, visibility, project/workspace/session, viewport or pane-focus changes and every five seconds while connected; after fifteen seconds without presence the claim expires. Blur/invisibility/disconnect releases immediately. If two machines both claim focus, the latest focus transition wins; another transition is the deliberate way to claim again. This follows the window Marcus is using even when its content pane has no terminal geometry lease. The selected claim is announced on the local `uirequest` bus under `$STATE/viewers/api-screen.json` with `uiRequestRelayV1`, the API PID and a two-second refreshed expiry. Only this ephemeral record is new; the TUI's saved state and tmux geometry lease are not rewritten.

A focused API viewer takes precedence for local `sidecar open` and `sidecar layout get|apply|move`. Each bus request is pinned to that connection; project Workspaces and Sessions TUIs ignore pinned requests. When API windows are unfocused, the existing TUI and remote-lease rules apply unchanged; only when neither a local TUI nor a connected remote lease holder could answer does the CLI decline (exit 4), never queue. Pinned requests are never relayed to a remote viewer. A `--sessions` request declines: the browser has no Sessions surface. Expired/disconnected claims fall back to the existing no-instance/lease refusal rules. A viewer that lacks the capability never registers a claim. A different project/workspace, off-screen origin session, busy viewer, lost focus or content-boundary failure earns a declined acknowledgement (exit 4). Remote host relays retain their existing owning-host transport; this registration targets local owning projects, consistent with the U3 content API, and never reads a remote root as local content.

A `ui_request` carries `{id, origin_pane?, action:"open"|"layout", project, workspace?, request:uirequest.Request, document:{layout}, etag, expires_at}`. The server plans open, additive batches, full specs and moves with the shared `panelayout`/`layoutapply` rules against a copy of the credential holder's U3 layout. File, issue, note and diff panes work. Files are converted to root-relative references and revalidated through the content root boundary, including traversal and symlink checks. Saved references are untrusted and are checked again before acceptance. The viewport and per-kind minimum outer floors are CSS pixels (160 by 96); `layout get` returns the existing version-1 grid report with `surface:"browser"`, `viewport_css_pixels:{width,height}` and `floors_unit:"css_pixels"`, without terminal-cell `viewport` or per-pane `box`. Duplicate leaves are reported by node identity. The full spec retains its existing one-primary/live-leaf grammar: layouts with multiple primary terminals cannot be replaced by a spec that would omit them. Non-grid layouts report `grid:null` and their raw tree.

Relay matching first finds live leaves with `session` exactly equal to `request.origin.tmuxSession`. A single matching leaf works with or without an attachment. When several leaves share that session, the request must carry optional `origin.tmuxPane`, and exactly one matching leaf's `attachment.expected_target` must have that same session and pane. Missing, unmatched or duplicate pane hints decline with a plain ambiguity reason, without changing the preference. Attachment hints cannot make a different session eligible. `origin_pane` identifies the selected leaf by node number in the pre-proposal tree's deterministic depth-first preorder; it is omitted for project-origin requests without a session. The CLI supplies `tmuxPane` only when a live tmux read independently confirms that its calling pane belongs to the resolved session/socket; targeting another shell supplies no pane hint. Clients still check that the origin candidate is displayed before accepting a proposal.

`sidecar layout get --json` exposes attachments as opaque data in both grid panes and the raw tree. `layout apply --spec` preserves each carried primary/live-shell leaf's saved attachment and display name, even when it moves. A CLI spec cannot create or replace an attachment hint: new leaves have none. Full specs retain the one-primary and live-leaf-cap rules; a tree they cannot carry in full declines unchanged. Open, additive apply and move proposals preserve attachment data on every existing leaf.

Resource/provider panes and new `shell` run/type descriptors decline in this version: U3 has no resource content route, and `ui:control` must not execute shell commands. Create shells through the `workspace:write` operations first, then carry an already displayed shell by its session in a spec. A full spec must carry each displayed live shell; it cannot close processes. None of these declines modifies the saved layout.

On receipt, the client checks `expires_at`, verifies that the same origin is still on its screen, adopts the proposed document without issuing a competing PUT, then sends `POST /api/v0/viewers/ack` with `{viewer_id,id,status:"opened"|"declined",reason?}`. `opened` means the client accepted the proposal; the server retains the planner's precise opened/retargeted/moved/unchanged verdict for the CLI. The response is `{document,etag}`. Accepted proposals are saved with the proposal's ETag and the bus ack is written only after that conditional save. A get request still needs the client acknowledgement; its report is returned in the CLI ack. The client must reconcile with the saved layout after a refusal, failed/uncertain acknowledgement, focus loss or reconnect. Never retry an uncertain ack or automatically replay agent actions.

The server rechecks credential ownership, presence, request expiry/existence, current project/worktree membership, content roots and the layout ETag at acknowledgement, even for a terminal-only tree. A removed or retargeted workspace declines before planning or saving; a membership/root change at acknowledgement returns 409 `content_changed`. Conflicts return 409 (`viewer_unavailable`, `request_unavailable`, `layout_changed` or `content_changed`) and decline the CLI request without saving the proposal. A client decline also leaves the store untouched. Its free-text `reason` reaches the CLI with control characters removed, capped at 512 bytes and prefixed as the viewer's decline; a saved layout whose leaf strings contain control characters declines every proposal until it is saved again without them. There is at most one unacknowledged proposal per viewer and one bounded outbound slot; a second request declines immediately. Disconnect, focus loss, expiry and CLI cleanup retire pending proposals. Requests are never accumulated for later delivery. The existing CLI exit codes remain 0 accepted (including unchanged), 2 usage, 3 no instance and 4 declined.

`testdata/ui-api/v0/viewer-exchange.json` and `viewer-worktree-exchange.json` record the typed project-root and worktree connection, presence, proposal and acknowledgement shapes; `layout-workspace-exchange.json` shows the matching scoped GET/PUT exchange. `layout-candidates.json` and `viewer-candidates-exchange.json` show distinct opaque candidates sharing one session and the exact origin-pane relay selection. `internal/tools/uiviewerproof` acts as a fixture client in `scripts/ui-api-proof.sh`: it drives the real `sidecar open` and layout get/apply/move against a private tmux/state server on port 0, proves scoped delivery, focused and late-ack declines, and rejects an outside-root path. The proof checks the shell’s durable `workDir` and catalog path, verifies that its shell-scoped layout shares the linked worktree preference, and repeats open/layout get/apply/move from the main checkout for a real linked Git worktree and a shell rooted there, saving and reading through `?workspace=…` and checking that the main preference stays unchanged. The worktree proof also opens two real panes in one private managed session with synthetic opaque hints, proves ambiguity refusal without a caller pane, and drives CLI get/spec/move/open with a verified caller pane while preserving both hints. A separate private worktree session supplies two real catalog candidates; its exact selectors and identities round-trip through HTTP layout storage, the local relay bus and the grid report. Managed shell sessions are excluded from worktree candidate discovery; CLI `--shell` targets registered shells, so the catalog-candidate relay leg uses the same owning bus directly. Actual browser rendering is the U4-b client lane.

## Client continuity across restart and upgrade

The browser keeps its non-extractable key in IndexedDB on its exact scheme, host and port, and a short-lived bearer in page memory. On restart, open pages lose their WebSockets and old bearers become unusable. An updated SDK obtains a fresh nonce, signs it with the stored key, receives a new bearer, gets new WebSocket tickets, and builds a fresh events/catalog baseline. A reloaded page reads the same IndexedDB key and follows that path without pairing again. Pairing codes, challenges, unused tickets, terminal handles and `api_instance` do not survive. The terminal client resolves/reconnects using the prior stable target identity, receives new handles and a fresh frame, and never replays input. Changing port or switching between `localhost` and `127.0.0.1` changes origin and requires its own pairing.

During a service-managed upgrade, executable replacement shuts down the old server cleanly and the manager starts the replacement against the same config and state tree. The browser sees a brief disconnect and follows the same signed-renewal path; a valid registered key does not require `sidecar api open` again. The foreground proof models the manager's restart without installing a service. Rebuilding the separate web UI needs no server restart: the next static request uses the replacement directory, and open pages continue until reload. Seamless reconnect and retaining selection are responsibilities of the updated SDK/client; a legacy client storing only a bearer must pair again and adopt this protocol.

## Schemas and fixture development

[ui-api.openapi.json](ui-api.openapi.json) is generated from the Go HTTP wire types, `uiapi.EventMessage` and `mobileproto.Request`/`Response`. Components use JSON Schema 2020-12; the terminal and events WebSockets are described under `x-streams`. The events upgrade reuses the Sessions query parameters and stream authentication parameters; it is GET-only. The generator uses `invopop/jsonschema` v0.13.0 because it reflects the same JSON tags used by `encoding/json` and supports the OpenAPI 3.1 schema dialect. Schema objects describe serialization; operation-specific field requirements, bounds, and ordering remain in this reference and [mobile-protocol.md](mobile-protocol.md). The route/method inventory and all schema references are checked, and a test fails if the committed document is stale. Regenerate the spec, fixture examples, checksums and CLI reference together with `./scripts/update-ui-api-contract.sh`. Staleness failures point to this same command.

Security alternatives describe only the listeners that serve an operation. Remote-only ticket issuance always requires credentials. The combined document uses `x-listeners` and `x-local-auth` to distinguish the Local socket's credential-free access from authenticated Browser and Tailnet requests on shared resources; clients must honor those listener annotations.

The CLI and HTTP catalog remain `mobileproto.CatalogSnapshot`. Status remains `uiapi.Status`; origin registration/list/revocation use the same named types on the CLI and HTTP. `CatalogRow.path` is optional in the generated schema. HTTP hello and pairing request bodies now also have named Go wire types instead of anonymous maps/structs.

`testdata/ui-api/v0/` contains synthetic HTTP hello, sessions, status, error, pairing, terminal and event examples with `SHA256SUMS`. Tokens, handles, paths and terminal text are synthetic. The terminal transcript is generated through the real mobile service with handles normalized. SDK tests can read the corpus directly. The same `./scripts/update-ui-api-contract.sh` command updates the resource inputs, records the real-Service terminal transcript, refreshes the checksums and verifies the corpus. Every JSON/JSONL corpus file is included in the manifest, including stream transcripts added by later lanes.

Fixture development requires `SIDECAR_ISOLATED_STATE=1` and temporary state/config paths. Startup refuses paths inside the real Sidecar state/config trees, including symlink aliases and API authority files linked into those trees, before it reads config or writes discovery. For an automatically cleaned proof run `./scripts/ui-api-fixture-proof.sh`. To develop a UI against a foreground fixture server:

```sh
fixture_root=$(mktemp -d /tmp/sc-fixtures.XXXXXX)
mkdir -p "$fixture_root/state" "$fixture_root/tmux"
printf '{}\n' > "$fixture_root/config.json"
unset TMUX TMUX_PANE
SIDECAR_ISOLATED_STATE=1 XDG_STATE_HOME="$fixture_root/state" TMUX_TMPDIR="$fixture_root/tmux" sidecar -config "$fixture_root/config.json" api serve --fixtures testdata/ui-api/v0 --port 0 --ui DIR
# After stopping the server, remove only this temporary tree.
rm -rf "$fixture_root"
```

`sessions.json` must contain an unfiltered Project-order catalog; queries use the real shared sorting/filtering/grouping functions. Ready rows use the deterministic synthetic identity issued by `mobile.FixtureIdentity`. `status.json` supplies recorded metadata, while listener addresses, `ui_dir`, and connected clients/attachments describe the actual running fixture server. Pairing codes, tokens, tickets and browser sessions are always issued by the real server; fixture examples are never usable credentials. All real listener authentication, Host/Origin guards, mutation guards, limits, static routing and shutdown behavior apply.

The fixture catalog includes a root shell and linked-worktree shell/worktree rows and candidates with `content_workspace_id`. Content, tree, layout and viewer-presence routes accept those selectors; shells and candidates sharing a root share its layout preference. Root selectors are empty or absent, and legacy `fixture-shell` and `fixture-project` IDs still select the configured fixture root from `workspace.json` (`/workspace/fixture` in the committed corpus). The legacy terminal's synthetic `expected_target` is unchanged. The linked worktree exposes two distinct deterministic echo candidates that resolve through the real terminal service. Linked selectors read the same immutable content examples under their owning fixture path and use separate layout preferences; fixture reads never reach the host filesystem.

Terminals run the real mobile protocol service against a capture/geometry adapter that echoes input bytes as normalized frames. Fixture panes are shared across connections to the same target and begin with an 80×24 grid and supports real request validation, control, input, resize/reset ordering, heartbeat, release and reconnect. Capability negotiation additionally enables presence arbitration through the shared lease policy, holder-label events, reset-free/coalesced frames, view-only input takeover and server paste. Server-paste bytes use the shared marker-removal and CRLF-normalization policy in [mobile-protocol.md](mobile-protocol.md#server-side-paste), including marker-only refusal; ordinary input bytes echo unchanged. No application is launched to interpret bracketed paste, and tmux's final newline translation and paste boundaries are absent from fixture output. It launches no shell and executes no commands. History is explicitly unavailable in this first echo adapter; it never falls through to tmux. Fixture mode is opt-in and does not replace the real backend unless `--fixtures DIR` is supplied.

### Per-user background service

The macOS adapter uses `github.com/ebitengine/purego` v0.11.1 to call the public libSystem `launch_activate_socket` API and free its descriptor array. This is a library API rather than a kernel syscall, so `x/sys/unix` alone cannot call it. A cgo adapter would break the release pipeline's `CGO_ENABLED=0` cross-builds; a separate compiled helper would add another executable that packaging and upgrades must keep aligned. `purego` supports both released macOS architectures and keeps that boundary in one small Go adapter. See [purego's supported platforms](https://github.com/ebitengine/purego) and [Apple's launch API header](https://github.com/apple-oss-distributions/launchd/blob/main/liblaunch/launch.h). Linux parses the documented [systemd descriptor protocol](https://github.com/systemd/systemd/blob/main/src/libsystemd/sd-daemon/sd-daemon.c) directly, with close-on-exec descriptors and environment cleanup; it needs neither libsystemd nor cgo.

`sidecar api service install [--ui DIR] [--json]`, `uninstall [--json]`, and `status [--json]` use one service-manager adapter: a launchd LaunchAgent on macOS, a systemd user service/socket pair on Linux. `install` writes a private definition, loads/enables it and starts it at login; repeating install unloads only that API job before replacing its definition. `uninstall` stops that job and removes its definition, preserving Sidecar state, browser sessions, paired origins and tmux. It is safe to repeat uninstall. No service command starts, stops or restarts tmux. Run as the login user without sudo. Linux needs a running systemd user manager; this command does not enable lingering or configure system services.

The macOS label is `com.haplab.sidecar.api`, in `~/Library/LaunchAgents/com.haplab.sidecar.api.plist`; the Linux units are `sidecar-api.service` and `sidecar-api.socket`, in `$XDG_CONFIG_HOME/systemd/user/` (default `~/.config/systemd/user/`). macOS stdout/stderr go to `$STATE/api/service.log`; Linux logs go to `journalctl --user -u sidecar-api.service`. Manager failures name the failed operation and where to inspect logs. A definition is retained if unloading fails, so a retry can recover it. An unrelated foreground API server causes install to refuse with its PID and instructions to stop that API process first; it is never killed by install. The refusal checks the held server lock even when discovery is missing, stale or unreadable (including a server still starting).

The definition records the current absolute `-config` path, state root and PATH, without inheriting tmux, agent identity or secrets. PATH keeps only absolute, existing directories owned by root or the user and not world-writable, so no other local user can plant a `tmux`, `git` or agent binary the service would run (empty, relative, missing, world-writable or foreign-owned entries are dropped; if none remain the job uses `/usr/bin:/bin:/usr/sbin:/sbin`). Its executable retains the launch/PATH symlink when that link names this exact binary. Use an installed stable `sidecar` link when installing, rather than a version-specific binary path. The service runs `sidecar -config PATH api serve`. Its manager binds the Browser socket at `127.0.0.1:7861` and the Local Unix socket at mode 0600 before launching the binary; it retains both across process restarts. Linux enables both units and the service requires the socket unit. The default Browser port remains 7861 and it does not enable Tailnet or change Tailscale configuration. `install --ui DIR` validates a directory containing a regular `index.html`, resolves it to an absolute path, and saves it as `api.uiDir` through the config writer while preserving unrelated keys, including other API settings. Symlink paths such as `current` are preserved for atomic UI upgrades. Config writes resolve an existing config symlink, write and sync a temporary file beside its target with the existing mode, then atomically rename it over the target; the symlink itself is preserved. A missing directory or index refuses before changing config or installing. `install --ui ""` clears the setting; omitting the flag keeps it. The static UI directory comes from config `api.uiDir`. Both foreground and service starts read it; explicit `serve --ui DIR` overrides it (an empty value disables it). Prefer an absolute UI directory with `index.html`. Config changes take effect at the next server start; rerun install to restart with changed config.

The release pipeline renders a Homebrew `service` block from `packaging/homebrew/sidecar.rb.tmpl`. `brew services start sidecar` on macOS uses the same label, a named `browser` launchd socket and `sidecar api serve` command, following the Homebrew-prefix `bin/sidecar` link that `make install-local` and `make install-worktree` activate. Choose either `brew services` or `api service` as the manager of that job; switching managers means stopping/uninstalling the old one first. Homebrew services use the default Sidecar config/state paths and activate the Browser socket; the process binds Local itself. Homebrew's Linux service generator cannot emit a `.socket` unit and its generated service fails closed without an inherited Browser listener. Use `sidecar api service install` on Linux; the formula prints that caveat.

Every `serve` watches the original stable executable path once per second. An atomic binary replacement, symlink retarget, or changed executable size/mtime logs the replacement and shuts down normally: WebSockets close, attachments release, process listener copies close and discovery is removed (manager listeners and inherited Unix socket paths remain), then launchd's KeepAlive or systemd's Restart=always launches the new binary. A briefly missing path during upgrade is ignored until a replacement exists. A foreground `serve` also exits cleanly on replacement; its caller must restart it. No restart changes tmux. Public-key browser registrations and paired-origin token hashes survive in the same state tree. Browser bearers do not survive; signed renewal avoids pairing again while the registered key remains valid and the browser uses the same exact origin. Socket activation protects the origin itself independently of that credential format. The reservation does not promise uninterrupted request delivery: WebSockets still close and clients reconnect after restart.

`status --json` reports the manager's job, including when it is absent or stopped (exit 0):

```json
{"manager":"launchd","label":"com.haplab.sidecar.api","file":"/…/Library/LaunchAgents/com.haplab.sidecar.api.plist","installed":true,"loaded":true,"running":true,"pid":4242,"version":"v1.16.0","ui_dir":"/…/sidecar/ui/current","last_exit":{"code":0},"socket":{"file":"/…/Library/LaunchAgents/com.haplab.sidecar.api.plist","installed":true,"loaded":true,"listening":true},"log":"/…/api/service.log","message":"API service is running; open it with `sidecar api open`."}
```

Service status `ui_dir` is the configured `api.uiDir`, or an empty string for API-only serving. If config cannot be loaded, service status still succeeds with `ui_dir:null` and `ui_config_error` explaining the failure; text output shows an unknown directory and that detail. Install requires valid config, while uninstall does not load it and reports an unknown UI directory. `sidecar api status` reads the Local socket and reports `ui_dir` from the running server, including any foreground `--ui` override. HTTP status includes `ui_configured` on every listener, but includes the `ui_dir` path only on Local; Browser and Tailnet omit it. Service status reports the saved config even when the service is stopped. If installation fails after saving `--ui`, the config remains saved so a retry can use it. With no UI directory, `GET /` serves a static HTML page with setup instructions and links to the public [build-your-own UI guide](https://sidecar.haplab.com/docs/build-your-own-ui) and [web UI setup](https://sidecar.haplab.com/docs/web-ui).

`installed` means the definition exists, `loaded` means the manager reports it loaded, and `running` means the manager reports a running process with a positive PID. A stopped job has PID 0. `version` is the running server version read through the Local API only when its PID matches the manager; it is an empty string when unknown, stopped, or still starting. `last_exit` is null when the manager has no termination record, otherwise `{code, signal?}`; a signal termination carries `code: 0` and the manager's signal name or number. A healthy current process can retain a previous failed exit record. `socket` reports its definition path, whether that definition is installed, whether the manager has it loaded, and whether the manager holds the Browser socket. On macOS it shares the LaunchAgent file and the loaded job reports its `browser` socket; on Linux it is the separate `.socket` unit, active in `listening` or `running` state. A running legacy service with no manager-held Browser socket reports an actionable reinstall message. The socket can remain listening while the API process is stopped or restarting; this reserves the origin without claiming API readiness. Install/uninstall with `--json` return the same status shape after the operation. Manager errors exit 1 with an actionable stderr message, usage errors exit 2. Installation can return a loaded job before its asynchronous startup finishes; use `api status` to verify API readiness.

Service-manager access is refused under `SIDECAR_ISOLATED_STATE=1`. Tests inject fake managers and pass real sockets through `ExtraFiles`; proofs run foreground servers or a fake socket supervisor on port 0. No proof installs launchd or systemd units.

## Notification centre

`GET /api/v0/notifications` returns `{notifications, unread, toast_ids, delivery_ids, delivery}`. The `access_request` source is a browser waiting for approval (see Approving a new browser); activating one should open the approval surface rather than a target. Notification records are the existing shared model: `id`, `source`, `severity`, `title`, `body`, `targets: [{kind,value,line?,project?,workspace?,routing_error?}]`, `createdAt`, `expiresAt`, `readAt`, and `dismissedAt`. Expiry removes a toast, never its centre entry. `toast_ids` applies the shared read/dismiss/expiry/source rules. `delivery` maps each ID to the shared native and sound decision, including quiet hours, foreground policy, freshness and cue; `delivery_ids` names records currently eligible for native or sound. Scoped file, issue and commit targets carry the resolved project and unchanged opaque workspace selector from their producing catalog row. File paths are relative to that workspace. A missing, changed or ambiguous origin carries `routing_error`; clients show that refusal instead of opening the currently selected project. Resolve targets through the public project content boundary; do not read host paths directly.

Request `?notifications=1` only after the HTTP hello advertises the `notifications` capability; omit it for older servers. The existing events socket advertises `notifications` and sends `type: "notifications", notifications: {notifications, unread, toast_ids, delivery_ids, delivery}` at connection and on notification/config changes. Snapshots coalesce and include current authoritative state after create, read and dismiss. The API’s existing local observer forwards settled agent transitions from the shared LaneTracker into the centre; authenticated managed-host live transitions use the same transport-neutral adapter as the TUI, respecting the shared SSH opt-in, freshness, dedupe and withdrawals. Agent records without explicit targets receive an exact owning catalog session ID, including remote sessions, or an explicit routing refusal; notifications-capable clients use those records for agent alerts and retain attention-event delivery only for older servers. Filesystem watches observe CLI and TUI changes; browser clients do not poll. Reconnect reconciles from the new baseline. Native/sound eligibility suppresses old discoveries outside the shared 15-second grace window.

`POST /api/v0/notifications/read` and `/dismiss` take `{id}` and return a current snapshot; an unknown `id` is 404. Servers whose HTTP hello advertises `notifications_batch` also accept `{ids: [...]}` (up to 1000) and apply the whole batch as one store change, so a cleared group or "Clear all" produces one watcher wake and one pushed snapshot instead of one per record. A batch skips unknown and already-settled ids rather than failing, because the requested state already holds for them; an empty `ids`, an empty id string, or `id` and `ids` together is 400. Clients send explicit ids rather than a selector so a notification that arrives after the user looked is never cleared unseen. Without the capability, clients fall back to one `{id}` request per record. `sidecar notify dismiss ID [ID...]` is the matching non-interactive path for a caller's own notifications. `GET` and `PUT /api/v0/notifications/settings` read/write the shared `NotificationsConfig`: native mode/provider, sound mode/cue paths, quiet hours, SSH policy and per-source toast/native/sound/expiry overrides. Saves validate through the existing config core and notify TUI consumers to reload. A refused save is `400 invalid_request` with `error.field` naming the dotted path of the refused field (`quietHours.start`, `sound.donePath`, `sources.agent.expiry`) so a form can show the refusal beside that control; the message begins with `notifications.<field>`. Nothing is written on refusal. `GET /api/v0/notifications/settings/options` returns what a settings form needs beside the stored config: `writable` (whether this credential may `PUT`) and the registered `sources`, loudest first, each with `id`, a human `title` and `description`, and its built-in `defaults` (`toast`, `native`, `sound` cue, and `expiry` as a Go duration or `sticky`). An override in `sources` replaces only the fields it names; clients should present the default for the rest rather than hardcoding the source list. Reads require `content:read` or `ui:control`; writes require `ui:control` (or `full`). Existing origin, bearer and JSON mutation guards apply. `sidecar notify read ID [--json]` supplies the same non-interactive mark-read capability.

Before showing a toast or using an external browser channel, `POST /api/v0/notifications/claim` with `{id, channel: "toast"|"native"|"sound"}`. `{claimed:true}` reserves that channel through the shared durable delivery ledger; another tab or host delivery cannot claim it simultaneously. Then report the actual result with `POST /api/v0/notifications/receipt` and `{id, channel?, succeeded?, error?, viewer_id?}`. Channel defaults to toast and succeeded defaults to true. A receipt requires the authenticated client's own outstanding claim. An actual successful toast receipt from the current matching screen acknowledges a relayed `notify post`; merely opening an events socket does not set `delivered:true`. While a browser holds the focused screen relay and has a live notifications subscription, the TUI keeps centre entries but suppresses its own toast column. Legacy relay-only browsers do not suppress TUI delivery.

### Pane-request deadlines and applied lines

`open` and `layout` wait six seconds by default. A relayed request's `expires_at` matches the caller's wait budget. The viewer checks it immediately before application, declines expired requests and rolls back a proposal if its acknowledgement is rejected. On timeout, the CLI cancels the request and returns exit 5 with JSON `reason: "viewer_timeout"`; it says that the connected viewer did not acknowledge, rather than claiming no instance exists. Final CLI acknowledgement read/cancellation is serialized with the server's layout commit and acknowledgement so a successful commit cannot be reported as an unacknowledged failure. Requests are never replayed on reconnect.

`ViewerAckRequest.line` is optional `{requested: number, applied: boolean, reason?: string}`. The server accepts a line outcome only when it matches the requested source line. CLI `open --json` includes this as top-level `line` and in the acknowledgement; human output says `Scrolled to line N` only on explicit applied confirmation and explains an unapplied or unconfirmed line. Older viewers remain usable and truthfully report that source navigation was not confirmed.

Issue content cards additionally project td's dependency IDs, unresolved blocker IDs, latest handoff, review history and implementer/reviewer/requester session fields. These fields and progress logs cross the public content DTO; the UI does not invoke td or infer lifecycle state from description text.
