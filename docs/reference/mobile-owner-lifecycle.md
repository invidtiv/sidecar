# Mobile owner stream lifecycle

A long-lived hub keeps one warm catalog stream per registered remote host. Each catalog request still collects and validates a fresh snapshot; only the connection is reused. Concurrent requests serialize on that host, and a canceled caller leaves a late reply to be drained before the next request. Genuine transport or protocol loss, a changed registration or owner incarnation, host removal or disablement, and backend shutdown retire the connection. Terminal connections remain separate because their hello negotiation, viewer identity, attachments, and geometry leases belong to the individual viewer.

Catalog authorization uses a collection-local worktree-state index. The index reads and resolves each saved project registration once, then resolves each queried root once. It preserves exact-spelling priority, filesystem-proven case aliases, and the original registration identity of removed or repointed aliases. A new collection creates a new index; filesystem or registration changes are never hidden behind a process-wide cache.

An owner-only stdio process observes stdin EOF and outbound failure independently of request handling. Its input queue holds at most eight complete requests and 16 MiB of encoded request bytes; overflow ends the transport. Clean EOF drains complete queued requests in order. Attachment and manager cleanup wait at most one second. The stdio runner allows three seconds after transport loss or cancellation for the final request and cleanup, then returns even if a backend ignores cancellation. It also checks the original parent once per second, so a reparented owner exits even if SSH keeps its input pipe open. These process-exit bounds apply to `mobile serve --stdio --owner-only`; in-process API services use bounded cleanup without a process-wide exit watchdog.

## Regression proof

`TestMobileOwnerIdleCPU` measures CPU time in a real owner-service subprocess over a fixed two-second idle window after hello. `TestWorktreeIndexStaleRegistrationCPUWindow` guards catalog authorization against repeated stale-registration path resolution: 100 root lookups across 400 stale registrations must finish within two seconds and consume at most 400 ms of CPU. The baseline consumed 2.337 seconds of process CPU without finishing that window; the indexed candidate finished using 86 ms. The warm-stream regression queries a remote owner repeatedly over a fixed window and requires one process start, including cancellation and reconnect coverage.

Run `./scripts/test-mobile-owner-ssh.sh` for the real OpenSSH ControlMaster proof. It starts a private loopback SSH server with temporary keys, a temporary control socket, and isolated Sidecar configuration, state, and tmux paths. Four owners complete hello and catalog requests for each of stdin EOF, SSH slave termination, and master termination; no remote owner may survive five seconds. The command needs `sshd`, `ssh`, and `ssh-keygen`, and does not change the machine's SSH service or default tmux server. Separate regressions cover stalled attachment cleanup and a blocked handler with another queued request before EOF.

The October 7 live CPU sample traced the apparently idle owners into catalog authorization: `Service.sessions` → `QueryCatalog.authorizeCatalogRows` → `shellTargetLookup.scan` → `managedtarget.CandidatesWith` → `WorktreeIndex.Lookup` → `findByMeta` → `sameProjectRoot` → `resolvedPath`. The owner had 405 saved project registrations; repeatedly resolving those records for each configured root accounted for the filesystem-heavy CPU load. Hello-only isolated owners already parked normally, so the fix targets the catalog lookup work alongside the idle CPU guard.
